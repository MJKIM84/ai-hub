# 23. 업무 시스템 연동 — 대표 접근법과 기술

<!-- auto:page-status:end -->

## 1. 세 줄 요약

- 로봇 인터페이스가 제공하는 변경 수단은 주문 갱신·일시정지·취소·중단·되감기 정도이므로, 우선순위 변경 규칙과 상위 지시의 번역은 ROP 쪽 대기열·재계획 로직이 맡아야 할 것으로 보인다. [추정][^ref-031][^ref-125] 아래는 이번 조사에서 확인한 수단과 연구 접근이다.
- 이 페이지는 [23. 업무 시스템 연동](../../categories/integration/business-system-integration.md) 페이지의 "대표 접근법과 기술" 절이 분량 기준을 넘어 옮겨 온 것이다. 원 페이지의 검증을 거친 내용이며 새 주장은 없다.

## 2. 배경

[23. 업무 시스템 연동](../../categories/integration/business-system-integration.md) 페이지를 쓰는 과정에서 "대표 접근법과 기술" 절의 분량이 세부영역 페이지 기준(4,000자)을 넘어, 내용을 줄이지 않고 이 주제 페이지로 분리했다.

## 3. 본문

로봇 인터페이스가 제공하는 변경 수단은 주문 갱신·일시정지·취소·중단·되감기 정도이므로, 우선순위 변경 규칙과 상위 지시의 번역은 ROP 쪽 대기열·재계획 로직이 맡아야 할 것으로 보인다. [추정][^ref-031][^ref-125] 아래는 이번 조사에서 확인한 수단과 연구 접근이다.


### 요청 응답과 상태 통지·취소 결과 나누기

Open-RMF rmf_api_msgs 의 작업 배정 응답(dispatch_task_response) 스키마는 성공 분기에서 success 와 작업 상태(task_state 를 따르는 state)를 필수로 요구하고, 실패 분기에는 실패 이유를 담는 errors 배열을 둔다(커밋 e9b7630 고정본, 2026-10-11 확인). [사실][^ref-1453] 같은 저장소의 취소 응답(cancel_task_response)은 자체 필드 없이 simple_response 를 참조하며, simple_response 는 성공이면 success=true 만, 실패면 success=false 와 errors 를 필수로 요구한다. [사실][^ref-1454][^ref-1455] 따라서 취소 응답은 요청 처리의 성패만 알리고, 작업이 실제로 멈춰 canceled 상태가 됐는지는 작업 상태를 따로 관측해 확인해야 할 것으로 보인다. [추정][^ref-1454][^ref-1455]

SAP Warehouse Robotics 는 SAP BTP 위에 만든 제품으로 SAP EWM 과 다른 제품이며, SAP EWM 사용자가 로봇을 통합하는 데 쓴다. 이 제품의 제조사 관제(FMS) 연동 API 문서(2024-07-10 판)는 그 API 를 폐기(Deprecated)로 표시한다. [사실][^ref-1456][^ref-1458] 아래 내용은 이 폐기 문서의 계약이며 현재 권장 계약이 아니다. 문서는 FMS 가 요청에 대한 응답을 관련 콜백 메서드 호출보다 먼저 돌려주도록 요구한다(요청 → 응답 → 콜백 순서). [사실][^ref-1456] 취소 절차에서 FMS 는 로봇 작업 취소에 성공하면 Update Robot Task Status 로 taskStatus 를 CANCELLED 로 알리고, 취소할 수 없으면 별도 메서드 Update Robot Task Cancelation Status 로 알린다. [사실][^ref-1456] 공통 메시지는 UUID 형식의 messageId 를 필수로 두고 작업은 별도의 robotTaskId 로 가리켜 메시지 식별과 작업 식별을 나누지만, 중복 제거·재시도 보장은 문서에 없다. [사실][^ref-1456]

구축자 의견으로는 업무 시스템–관제 인터페이스를 비교할 때 ‘접수 응답’, ‘진행 통지(콜백·상태)’, ‘취소 결과’, ‘업무 확정’을 따로 보는 것이 좋아 보이며, SAP 현재 권장 연동 경로의 계약은 이번에 확인하지 못했다. [의견][^ref-1456][^ref-1453][^ref-1454] 또 구축자 의견으로는 업무 쪽 ‘취소’를 로봇 명령 하나로 옮기기 전에 작업의 현재 상태(시작 전·실행 중·종료 후), 지울 기록과 남길 이력, 실행 종료 뒤 후처리 여부를 먼저 정해야 할 것으로 보인다. OPC Job Control 상태와 VDA 5050·Open-RMF 상태의 표준 매핑은 찾지 못했다(oq-020). [의견][^ref-131]

### 우선순위 변경의 허용 상태·권한·정렬

Oracle WMS Cloud 26c REST API 의 작업 우선순위 변경(Change Task Priority) API 는 Ready·Held·Created 상태인 작업의 우선순위만 바꿀 수 있다고 명시한다. [사실][^ref-1457] 외부 시스템도 다른 작업의 긴급도에 따라 작업 우선순위를 바꿀 수 있지만, Task/Change task priority 권한이 켜져 있을 때만 쓸 수 있다. [사실][^ref-1457]

SAP Warehouse Robotics 의 integration services 경로 문서(판 2308)는 위 FMS 연동 API 와 다른 연동 경로다. 이 문서는 로봇 배정 최적화를 켜지 않으면 로봇이 속한 자원 그룹의 큐 순서를 따르고(첫 큐를 끝내야 다음 큐), 큐 안의 창고 오더를 latest starting date(LSD) 순으로, LSD 가 없으면 생성 시각 순으로 정렬한다고 설명한다. [사실][^ref-1458]

구축자 의견으로는 우선순위 변경 가능 여부를 업무 작업의 상태와 로봇 실행 단계에 대해 따로 검사하고, 대기열 재정렬과 진행 중 작업 선점은 별도 정책으로 두는 것이 좋아 보인다. 진행 중 작업의 재정렬 방법과 업체 간 우선순위 숫자의 대응은 확인하지 못했다(oq-019). [의견][^ref-1457][^ref-1458]

### 업무 객체 해석과 MCP 같은 새 접점

SAP Architecture Center 의 참조구조(2026-05-12 갱신)는 이송 오더를 만들고 관리하지만 물건을 집지는 못하는 디지털 warehouse AI agents 와 구별해, Embodied AI agents 의 세 가지 주요 skill 가운데 하나로 업무 객체의 의미 이해(주문 우선순위·취급 요건 같은 WMS 데이터 속성이 물리 작업 실행에 뜻하는 바)를 든다. [사실][^ref-1461] SAP 뉴스(2025-11-05 게시)는 Bosch·Aimbo 공동 개념검증에서 Aimbo 의 휴머노이드 Anigon 1대가 SAP EWM 의 배송 정보·주문 우선순위·보관 위치를 업무 문맥으로 받아 창고 작업을 수행했다고 소개하며, 이 사업은 탐색 단계로 전용 beta·test 시스템 환경에서 검증됐다. [추정] 벤더 주장[^ref-1462] 이 영역에서는 두 자료를 업무 객체를 실행 조건으로 해석하는 계층의 예로만 보며, 휴머노이드의 작업 수행 자체는 [44. 로봇 기반 모델·언어 모델 계획](../../categories/ai-and-learning/robot-foundation-models-and-llm-planning.md)에서 다룬다.

NVIDIA Isaac Mission Dispatch README(커밋 56455eb 고정본)는 2026-03 에 Mission Dispatch MCP 추가를, 2026-08 에 VDA5050 3.0 지원과 generic action node 추가를 기록한다. [사실][^ref-1341] 같은 커밋의 [모델 컨텍스트 프로토콜(MCP)](../../glossary/model-context-protocol.md) 서버는 조회 도구(로봇 상태·미션 상태·미션 중 로봇·유휴 로봇·플릿 요약·로봇 건강 점검·미션 큐·최근 실패), 연결 시험, 로봇 등록, 좌표 이동 미션 전송까지 도구 11개를 등록하며 미션 취소 도구는 없다. [사실][^ref-1341] 이동 미션 도구는 경유점 하나짜리 경로 미션 트리와 timeout·deadline 을 담아 Mission Dispatch REST API 의 mission 경로로 보낸다. [사실][^ref-1341] robotmcp 의 ROS-MCP 데모 예제(커밋 edbc642 고정본)는 Ubuntu 22.04·ROS 2 Humble·Ignition Gazebo Fortress 의 창고 시뮬레이션에서 Tugbot 1대를 자연어로 이동시키고 라이다·주행거리 센서와 위치를 조회하는 예시이며, 업무 시스템 연동은 없다. [사실][^ref-1463]

구축자 의견으로는 MCP 를 업무 요청의 접점으로 평가할 때 공개 코드가 주는 도구 범위(조회·등록·좌표 이동, 취소 없음)와 업무 요구(주문 ID 대응·허용 상태 검사·실행 전 승인·결과 대조·취소)를 따로 확인해야 하며, 공개 코드의 존재를 다사업자 WMS 주문·재고 처리의 운영 검증으로 볼 수 없다. [의견][^ref-1341][^ref-1463] 대화로 만든 지시를 사람이 승인한 계획으로만 실행하는 문제는 [12. 채팅으로 업무 지시·오케스트레이션](../../categories/chat-based-configuration-and-operation/chat-task-instruction-and-orchestration.md)에서 다루고, 여기서는 업무 요청 접점의 범위만 본다.
