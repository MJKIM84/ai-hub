# 사용자 실험 결과 입력 (experiments/)

이 폴더는 중점 연구 트랙의 실험 결과를 사용자가 직접 넣는 곳이다. 규칙의 근거는 빌드 사양서 8.2 "트랙 공통 운영 규칙"의 실험 항목이다.

## 규칙

1. **실험은 사용자가 직접 수행한다.** 에이전트는 실험을 수행하지 않는다.
2. **실험 계획은 스토리텔러가 제안한다.** 단계 3. 비정형 문서에서 온톨로지를 추출하는 방법 조사(docs/tracks/manual-capability-ontology/stage-3-extraction-methods.md), 단계 5. 완전성과 정확성을 검증하는 방법 조사(docs/tracks/manual-capability-ontology/stage-5-completeness-verification.md), 단계 7. ROP 활용 시나리오 종합과 가설 판정(docs/tracks/manual-capability-ontology/stage-7-rop-scenarios-and-hypotheses.md)에서 docs/tracks/manual-capability-ontology/experiments.md 에 실험 계획을 제안한다. 사용자는 그 계획을 따르거나 자기 실험을 설계해도 된다.
3. **결과는 `experiments/<날짜>-<이름>/` 폴더에 넣는다.** 폴더마다 `README.md`(목적·방법·결과 요약)와 데이터 파일을 둔다.
4. **다음 트랙 실행에서 반영된다.** 스크립트가 이 폴더의 내용을 리서치 에이전트의 프롬프트 입력에 넣고, 리서치 에이전트가 그것을 발견 사항으로 만들며, 페이지에서는 `[사용자 실험]` 태그로 표시된다. `[사실]` 로 올라가려면 내용 검증 에이전트의 판정이 필요하다. 사용자가 결과를 넣었다는 것만으로 사실이 되지 않는다.
5. **충돌은 숨기지 않는다.** 실험 결과가 기존 발견 사항이나 온톨로지 초안과 충돌하면 출처 충돌과 같이 둘 다 제시되고 열린 질문(또는 트랙 질문 백로그)에 올라간다.
6. **"빠짐없이"는 측정 결과가 있을 때만.** 커버리지 같은 지표를 실제로 측정했다면 그 수치와 측정 조건을 적는다. 측정하지 않았으면 "빠짐없이", "완전", "모든 기능" 같은 표현을 쓰지 않는다.

## 폴더와 파일

```
experiments/
├─ README.md                                  # 이 안내
└─ 2026-10-15-amr-manual-extraction/          # 예: <날짜>-<이름>
   ├─ README.md                               # 목적·방법·결과 요약 (필수)
   ├─ extracted-capabilities.csv              # 데이터 파일 (자유)
   └─ notes.md                                # 추가 기록 (자유)
```

- 폴더 이름: `YYYY-MM-DD-<slug>`. 날짜는 실험을 수행한 날(또는 결과를 넣은 날), slug 는 영문 소문자·숫자·하이픈이다.
- `README.md` 는 필수이며 아래 서식을 따른다. 스크립트가 `README.md` 전체와 텍스트 데이터 파일(csv, json, md, txt)을 리서치 에이전트의 프롬프트 입력에 넣는다 [가정]. 에이전트는 파일을 직접 읽지 않으므로, 크거나 이진 형식인 파일(PDF, 이미지, 스프레드시트)은 입력에 들어가지 않을 수 있다. 핵심 결과는 `README.md` 에 요약해 둔다. 입력에 넣는 파일 형식의 최종 목록은 실행 스크립트(pipeline/agent_runner.py)의 규칙을 따른다. [가정]
- 제조사 문서 원문을 통째로 넣지 않는다. 문서 구조나 정보 형태의 사례로 필요한 부분만 짧게 발췌하고 출처(문서 이름, 버전, 페이지)를 적는다. 개인정보, 비공개 계약 자료, 고객 현장의 식별 정보도 넣지 않는다.
- 한 번 넣은 폴더는 고치지 않는다. 같은 실험을 다시 하면 새 날짜의 폴더를 만들고 `README.md` 에 이전 폴더를 적는다. [가정] 그래야 어느 실행이 어느 결과를 읽었는지 추적할 수 있다.

## `README.md` 서식

```markdown
# <실험 이름>

- 트랙: manual-capability-ontology
- 단계: 3                                   # 실험이 답하려는 단계 번호(1~7)
- 답하려는 질문: q3-02                       # 트랙 질문 백로그의 질문 id. 여러 개면 쉼표로 구분
- 실험 계획: experiments.md 의 계획 번호 또는 "자체 설계"
- 수행일: 2026-10-15
- 수행자: 이름 또는 역할
- 이전 실험: 없음                            # 같은 실험을 다시 한 경우 이전 폴더 이름

## 목적

무엇을 알아내려 했는가. 한두 문장.

## 방법

대상 문서·기종(공개 문서면 이름·버전·URL), 사용한 도구와 버전, 절차, 측정 방법. 다른 사람이 재현할 수 있을 만큼 적는다.

## 결과 요약

핵심 결과를 수치와 측정 조건과 함께 적는다. 예: "사용자 매뉴얼 v2.1(공개본) 48쪽 중 기능 서술 문장 132개를 표로 추출했고, 사람이 검토한 결과 118개가 맞았다(측정 조건: 기능 이름·전제조건·파라미터 세 항목이 모두 맞을 때 정답으로 집계)."

## 한계

측정하지 못한 것, 표본의 편향, 재현 조건의 제약.

## 데이터 파일

- extracted-capabilities.csv — 추출된 기능 목록(열: 기능 이름, 전제조건, 파라미터, 출처 페이지, 검토 결과)
- notes.md — 검토 중 발견한 문제
```

## 반영 흐름

1. 사용자가 `experiments/<날짜>-<이름>/` 을 만든다.
2. 다음 트랙 실행에서 스크립트가 이 폴더를 리서치 에이전트의 입력에 넣는다.
3. 리서치 에이전트가 결과를 발견 사항으로 만든다. JSON 발견 사항의 태그는 `추정`이고 출처 항목은 만들지 않으며(`source_ids`는 빈 배열), 근거 발췌 첫머리에 "사용자 실험 (experiments/<날짜>-<이름>/): "을 붙인다. 페이지에서는 스토리텔러가 `[사용자 실험]` 태그로 표시한다(agents/researcher.md 10.9절). 스키마의 발견 사항 태그가 사실·추정·의견뿐이어서 정한 방식이다. [가정]
4. 내용 검증 에이전트가 방법·측정 조건이 적혀 있는지, 기존 발견 사항·온톨로지 초안과 충돌하지 않는지 본다.
5. 스토리텔러 에이전트가 단계 페이지와 실험 페이지에 `[사용자 실험]` 태그로 반영하고, 온톨로지 초안 변경이 필요하면 근거 발견 사항 id 와 함께 제안한다.
6. 반영 결과는 트랙 로그(docs/tracks/manual-capability-ontology/log.md)와 변경 이력(docs/changelog.md)에 남는다.

관련 안내: docs/about/how-to-contribute.md(기여·정정 방법), docs/about/reading-guide.md(읽기 가이드의 `[사용자 실험]` 태그 설명), docs/tracks/manual-capability-ontology/experiments.md(실험 계획).
