# 시뮬레이션 검증 범위

<!-- auto:page-status:start -->
> 페이지 상태: published · 신뢰도: medium · 페이지 버전: 1 · 마지막 갱신: 2026-10-12 · 마지막 실행: 없음
<!-- auto:page-status:end -->

시뮬레이션에서 로봇이 통신 단절을 잘 견뎠다고 해서, 실제 승강기 안 통신 음영에서도 그렇다는 뜻은 아니다. 시뮬레이션은 **정해 준 사건에 시스템이 어떻게 대응하는지**를 시험할 수 있지만, **그 사건이 현장에서 왜 생기는지**를 재현하는 것은 다른 문제다. 이 페이지는 두 검증을 나누고, 이 저장소의 로봇 시뮬레이터가 각각 어디까지 지원하는지 코드로 확인한 범위를 정리한다. 시뮬레이션 결과는 어떤 경우에도 현장 안전의 보증이 아니다.

## 1. 현장 문제

발표 관찰: 현장 실패(기름 바닥 미끄럼, 반사 재질 오인식, 위치 상실, 통신 단절, 승강기 상태 혼동)를 미리 시뮬레이션으로 검증할 수 있는지에 대한 관심이 소개됐다.

[의견] 두 가지 검증을 구분해야 한다.

1. **사건 주입**: 통신 끊김·관측 상실·승강기 지연을 입력으로 넣고, 감지 → 작업 보류 → 대체 → 재개의 논리가 맞는지 본다.
2. **실패 원인 재현**: 오염 접촉, 광학 반사·투과, 위치 추정 알고리즘, 전파·로밍이 실제 센서 출력과 같은 실패를 만들어 내는지 본다.

첫 번째에서 복구에 성공했다고 두 번째의 인과가 맞다는 증거가 되지 않는다. 물리 엔진이나 3D 장면이 있다고 필요한 모델·센서 처리·현장 보정·검증 자료가 저절로 생기지도 않는다.

## 2. 근거·적용 조건

**다중 로봇 시뮬레이션의 일반적 초점.** [사실] Open-RMF 문서는 slotcar 플러그인이 단순한 레일 같은("rail-like") 경유점 이동을 쓰며 교통 관리에 초점을 둔다고 설명한다.[^ref-406] 이 설명을 이 저장소의 별도 MuJoCo 시뮬레이터의 지원 범위로 옮기지 않는다.

**이 저장소의 시뮬레이터.** 저장소 코드 관찰: 기준 커밋 [9c4de24](https://github.com/MJKIM84/ai-hub/tree/9c4de242d0f08ac8804707b7cc7787fbd261fef4/robot-simulator)의 아래 파일·함수를 읽었다. 실행·수정·성능 측정은 하지 않았다.

| id | 위치 | 코드에서 확인한 것 | 이것으로 말할 수 없는 것 |
|---|---|---|---|
| C-SIM1 | [incidents.py](https://github.com/MJKIM84/ai-hub/blob/9c4de242d0f08ac8804707b7cc7787fbd261fef4/robot-simulator/src/robot_platform/incidents.py#L15) `IncidentScheduler.tick` | 시각·작업 상태·이벤트로 사건을 발동하고, 지속 시간 뒤 복구를 만든다. 예전 타이머가 새 고장을 지우지 않도록 소유자를 검사한다("A newer/manual fault owns this target") | 고장이 물리적으로 왜 생겼는지의 재현 |
| C-SIM2 | [sensing.py](https://github.com/MJKIM84/ai-hub/blob/9c4de242d0f08ac8804707b7cc7787fbd261fef4/robot-simulator/src/robot_platform/sensing.py#L15) `ObservationBus.sample/deliver` | 통신·센서 고장이나 탈락이면 관측을 만들지 않고, 위치·방향 잡음과 전달 지연(관측 지연 + 통신 지연)을 적용한다 | 실제 AP·전파·로밍·대역폭·큐·재접속 프로토콜의 검증 |
| C-SIM3 | [physics.py](https://github.com/MJKIM84/ai-hub/blob/9c4de242d0f08ac8804707b7cc7787fbd261fef4/robot-simulator/src/robot_platform/physics.py#L78) `_build`(78~241행), `_research_robot`(247~297행), `contacts`(523행) | MuJoCo 형상에 마찰 파라미터를 주고(바퀴·그리퍼 포함), 접촉 힘을 `mj_contactForce`로 읽는다 | 실제 기름막·발 패드의 마찰을 실측으로 보정했다는 증거 |
| C-SIM4 | [physics.py](https://github.com/MJKIM84/ai-hub/blob/9c4de242d0f08ac8804707b7cc7787fbd261fef4/robot-simulator/src/robot_platform/physics.py#L555) `range_scan` | 충돌 형상에 광선을 쏘는 평면 라이다 모델. 반환값에 "planar geometric rays; no material reflectance"라고 적혀 있다 | 재질 반사·투과·그림자로 인한 센서 실패의 원인 검증 |
| C-SIM5 | [physics.py](https://github.com/MJKIM84/ai-hub/blob/9c4de242d0f08ac8804707b7cc7787fbd261fef4/robot-simulator/src/robot_platform/physics.py#L577) `tracked_people` | 가려짐을 반영하는 단순화 센서이며 "This is not camera recognition"이라고 명시한다 | 카메라 인식 모델의 검증 |
| C-SIM6 | [physics.py](https://github.com/MJKIM84/ai-hub/blob/9c4de242d0f08ac8804707b7cc7787fbd261fef4/robot-simulator/src/robot_platform/physics.py#L419) `facility_observations`, [facilities.py](https://github.com/MJKIM84/ai-hub/blob/9c4de242d0f08ac8804707b7cc7787fbd261fef4/robot-simulator/src/robot_platform/facilities.py#L170) `recover/_fresh` | 설비 관측은 이상적인 센서로 설명되고("Explicit ideal facility sensors"), 설비 관리자는 관측 시각의 나이를 검사하며 새롭고 안전한 관측이 돌아와야 복구한다("fresh safe observations") | 실제 승강기 인증, 센서 고장률, 안전 성능 |

지원 범위는 위 파일·함수로 한정했다. 시뮬레이터 전체를 "그런 기능이 없다"고 증명하려고 전수 분석하지 않았다. "읽은 경로에서 원인 모델·보정 증거를 찾지 못했다"를 "시스템 전체에 없다"로 바꾸지 않는다.

## 3. ROP 판단

[의견] 증거 수준마다 보여 주는 것과 보여 주지 못하는 것이 다르다.

| 수준 | 보여 주는 것 | 보여 주지 못하는 것 |
|---|---|---|
| 문서·정적 코드 | 필드·조건문·상태 전이·함수 경로의 존재 | 실행 성공, 성능, 현장 안전 |
| 사건 주입·관측 재생 | 주어진 관측·고장에 정책이 어떻게 반응하는지 | 그 관측을 만든 실제 물리·광학·전파 원인 |
| 검증된 구성의 물리·센서 시뮬레이션 | 모델 가정과 보정 범위 안의 예측 | 범위 밖 재질·기체·펌웨어·현장으로의 일반화 |
| 실기체·현장 대조 | 해당 조건·표본에서의 재현과 예측 오차 | 모든 조건, 장기 신뢰성, 법적 적합성 |

[의견] ROP에서 시뮬레이션은 주로 첫 번째 검증, 즉 단절·지연·관측 상실·설비 상태 불일치에 대한 대응 정책을 시험하는 데 쓴다. 저장소 시뮬레이터의 C-SIM1·2·6 경로가 이 용도에 맞는 후보다. 원인 재현이 필요한 질문(반사로 생긴 가짜 장애물, 기름 위 미끄럼, 전파 음영)은 실측 자료와 별도 모델이 있어야 하며, 현재 읽은 코드 범위로는 다룰 수 없다.

## 4. 제조사·설비·운영자 역할

[의견] 원인 재현에는 시뮬레이션 담당만으로는 부족하다. 센서 원시 데이터와 노출·보정 설정은 센서·로봇 제조사가, 바닥 마찰·조명·무선 측정은 시설·네트워크 담당이, 설비 제어기 로그와 인터페이스 명세는 설비 업체가 제공해야 한다. 모델 담당은 이 자료를 보정용과 검증용으로 나누고 오차를 보고한다.

## 5. 대응·판단 기준

[의견] 사례별로 필요한 것은 다음과 같다.

| 사례 | 원인 재현에 필요한 모델 | 실측 보정 자료 | 사건 주입으로 할 수 있는 것과 한계 |
|---|---|---|---|
| 기름 미끄럼 | 마찰·접촉 모델, 기체 제어·보행·바퀴, 적재 동역학, 오염 영향 모델 | 마찰 시험, 패드·바퀴 상태, 오염 기록, 적재·속도 로그 | 고장·외력 사건에 대한 복구 정책 시험. 마찰 파라미터만으로 실제 기름 현상의 정확성을 주장하지 않는다 |
| 반사·투명·그림자 오인식 | 광학·깊이 센서 모델과 실제 인식 알고리즘 | 원시 센서·노출·보정, 재질, 조명 위치, 실물 치수 | 센서 고장으로 관측 누락 대응을 검토. C-SIM4의 기하 광선은 광학 원인 재현 근거가 아니다 |
| 위치 추정 실패 | 실제 위치 추정 알고리즘, 센서 관측 생성, 지도, 재위치 추정 절차 | 기준 측량, 동기화, 원시 데이터, 지도·설정 판, 환경 변화 기록 | 위치 잡음·관측 결손으로 상위 대응 검토. 실제 알고리즘이 위치를 잃는 인과와 다르다 |
| 통신 단절 | 전파·네트워크·큐 모델 또는 측정 기반 채널 모델, 실제 프로토콜 세션 | 승강기 안팎·문 상태별 무선·패킷·애플리케이션 시각·부하 | C-SIM2의 고정 지연·관측 결손으로 정책 민감도 시험. 전파 원인과 재접속 보장을 증명하지 않는다 |
| 승강기 상태 불확실 | 설비 상태 기계·인터페이스, 센서 오류·시각·관측 독립성 모델 | 제어기·문 센서·로봇·ROP의 동기 로그, 업체 인터페이스 명세, 현장 시험 | C-SIM6에서 오래된 관측 검사 경로 확인. 이상적 센서 모델을 실제 설비 안전 평가로 넓히지 않는다 |

[의견] 보정과 검증은 다음 순서로 분리한다.

1. 실패 가설과 대안 가설을 적고 입력·관측·판정 단위를 고정한다.
2. 실측 자료를 보정용과 독립 검증용으로 나눈다. 같은 로그에 맞춘 오차를 현장 예측력으로 보고하지 않는다.
3. 좌표·단위·샘플링·시계 오차·센서 보정판을 맞춘다.
4. 보정한 파라미터, 측정 불확실성, 모델이 생략한 현상을 기록한다.
5. 정상·경계·실패·회복 조건별로 궤적·검출·지연·업무 결과를 비교한다.
6. 허용 오차는 업무·안전 요구에서 정하고, 결과를 본 뒤 합격선을 고치지 않는다.
7. 맞추지 못한 실패와 다른 조건의 홀드아웃 결과까지 보고한다.
8. 기체·센서·펌웨어·설정·설비가 바뀌면 영향 범위와 재검증 목록을 갱신한다.

## 6. 검증·한계

- 시뮬레이터를 실행하지 않았고, 기존 테스트도 돌리지 않았으며, 모델 파라미터를 바꾸거나 현장 데이터로 보정하지 않았다.
- 코드 관찰은 기준 커밋의 해당 함수 범위다. 이후 커밋에서 바뀔 수 있다.
- 시뮬레이션 통과는 현장 안전, 인증, 운영 승인의 근거가 아니다. 이 페이지의 표는 시험 설계를 위한 것이다.

- 시뮬레이터가 실패의 원인을 어느 수준까지 재현하는가? 물리·센서·전파별 입력·관측·오차·보정 범위와 재현하지 못한 사례를 함께 보고할 수 있는가? (FR09)
