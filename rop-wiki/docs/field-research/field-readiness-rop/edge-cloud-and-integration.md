# 엣지·클라우드와 연동 계약

<!-- auto:page-status:start -->
> 페이지 상태: published · 신뢰도: medium · 페이지 버전: 1 · 마지막 갱신: 2026-10-12 · 마지막 실행: 없음
<!-- auto:page-status:end -->

ROP는 업무 시스템과 로봇 사이에 서 있다. 위로는 MES·WMS가 일을 주고, 아래로는 제조사 관제(RCS·FMS)나 로봇 API, 문·승강기 같은 설비가 있다. 이 페이지는 그 사이에서 누가 무엇을 결정하는지, 여러 통신 기술이 각각 무엇을 보장하고 무엇을 보장하지 않는지, 통신이 끊기면 작업별로 무엇을 하는지를 정리한다.

## 1. 현장 문제

발표 관찰: 업무 시스템 → 오케스트레이션 플랫폼 → 연동 계층 → 제조사 관제 → 로봇·장치로 이어지는 계층 구조가 소개됐다. 제조사 관제 개념이 두 계층에 걸쳐 등장해 엄격한 표준 계층으로 보기는 어렵다. 여러 통신 기술(메시지 브로커, 스트리밍, RPC, 로봇 통신 규격, AI 에이전트 프로토콜)을 함께 쓴다는 설명과, 승강기 안 통신 음영 문제도 소개됐다.

발표 관찰: 약어로만 언급된 통신 방식 하나(PTT)는 정확한 철자·확장명·문서를 확인하지 못했다. 다른 표준의 오기로 추측해 고치지 않는다.

## 2. 근거·적용 조건

**로봇 통신 규격의 범위.** [사실] VDA 5050은 관제 시스템과 이동 로봇 사이의 통신 인터페이스를 정한다. 안전 요구, 교통 관리 논리(경로·우선순위·교착 해소), 주변 설비·인프라·외부 IT 시스템과의 인터페이스, 프로젝트 조정·구현 절차, 운영 책임 할당, 사이버보안은 범위 밖이라고 명시한다. 로봇이 브로커와 연결이 끊기면 주문 정보를 유지하고 마지막으로 확정된(released) 노드까지 수행한다.[^ref-031]

**기술별 역할.** 아래 표의 "원문에서 확인한 역할"은 [사실]이다. 나머지 두 열은 [의견]이다.

| 기술 | 원문에서 확인한 역할 | ROP 적용 해석 | 보장하지 않는 것 |
|---|---|---|---|
| gRPC | 기본 기한(deadline)을 두지 않으며 클라이언트·서버가 기한을 정한다[^ref-1581] | 명령 요청·상태 조회에 기한·취소·재조회를 설계 | 기한 만료는 실물 작업이 수행되지 않았다는 증명이 아니다 |
| MQTT 5.0 | 메시지 전달 등급 QoS 0(최대 한 번)·1(최소 한 번)·2(정확히 한 번)를 정한다[^ref-306] | 연결·상태·명령 토픽 계약과 세션·만료 정책 | QoS는 브로커 구간의 메시지 전달이다. 업무 완료나 실물 인계를 보장하지 않는다 |
| Kafka | 기본은 at-least-once이고, 외부 목적 시스템까지의 exactly-once는 일반적으로 그 시스템의 협조가 필요하다[^ref-1582] | 감사·이벤트 처리, 재생, 중복 판정 | 로봇 동작의 exactly-once를 자동으로 주지 않는다 |
| VDA 5050 | 관제–로봇 사이 주문·상태의 의미와 MQTT 사용 규칙[^ref-031] | 기종·판·지원 동작과 역할을 고정해 연동 | 설비·상위 업무·안전 규격을 대신하지 않는다 |
| MCP | LLM 애플리케이션을 외부 데이터 소스와 도구에 연결한다[^ref-1583] | 승인된 업무 요청 도구의 접점 | 물리 제어·실시간성·안전 적합성의 근거가 아니다 |
| A2A | 독립적이고 내부가 불투명할 수 있는 AI 에이전트 시스템 사이의 상호운용, Task·Message·Artifact 정의[^ref-1584] | 작업 협의·결과 전달 후보 | 로봇 사이의 물리적 인계·정지 규약과 같지 않다 |

[의견] 위 기술은 서로 다른 층에서 함께 쓰일 수 있다. "Kafka가 gRPC를 대체해 전달 문제를 해결한다"처럼 목적·전달 의미·지연·소유권을 빼고 우열을 비교하지 않는다.

## 3. ROP 판단

[의견] 발표의 계층 설명을 위키의 책임 경계에 맞춰 다시 쓰면 다음과 같다. 계층 이름은 발표의 설명 체계이며 표준 계층이 아니다.

| 층 | 책임 | 결정 주체 |
|---|---|---|
| 업무 시스템(MES·WMS) | 업무 요청, 우선순위, 인수 기준 | 업무 소유자가 주문·생산 요구를 결정 |
| 오케스트레이션 플랫폼(ROP) | 이종 자원 배정, 공용 자원, 상위 완료 판정, 대체 업무 | 위임받은 범위의 조율. 현장 승인 책임은 따로 있다 |
| 연동 계층·직접 로봇 API | 명령·상태·좌표·오류의 어댑터 계약 | 어댑터 구현자. 단순 중계와 실행 권한을 구별 |
| 제조사 관제(RCS·FMS) | 제조사 플릿 내부의 배차·경로·실행 | 제조사 관제. ROP와 배정·경로 권한이 겹치지 않게 한다 |
| 로봇·장치 | 주행·인식·동작·안전 정지 | 로봇 제어기·제조사 |
| 설비 제어(문·승강기·PLC) | 설비 운행과 안전 인터록 | 설비 제어기·시설 담당. ROP는 요청하고 상태를 확인한다 |

[의견] 연결이 끊긴 것을 정지가 끝난 것으로 해석하지 않는다. VDA 5050 규칙대로라면 로봇은 끊긴 뒤에도 확정된 노드까지 움직인다. 또 VDA 5050을 채택했다고 설비 연동이나 운영 책임이 정해지지 않는다. 규격이 그 둘을 범위 밖으로 두기 때문이다.

## 4. 제조사·설비·운영자 역할

[의견] 업무 소유자는 작업 마감과 품질 기준을, 현장 IT·네트워크 업체는 무선·백홀의 측정과 유지를, 제조사는 단절 시 로봇이 하는 일(계속·감속·정지)과 그 설정을, 설비 업체는 설비 상태 전송 주기와 수동 모드 동작을 문서로 정한다. ROP는 이 문서들을 모아 작업별 단절 정책으로 묶고, 정책이 실제로 지켜지는지 로그로 확인한다.

## 5. 대응·판단 기준

[의견] 허용 지연은 보편적인 밀리초 값이 아니라 현장 업무의 마감과 위험 분석에서 거꾸로 계산한다. 단방향 지연을 재려면 시계 오차도 함께 기록하고, 시계가 맞지 않는 환경에서는 왕복 시간과 따로 해석한다.

| 작업 | 지연·상태 신선도 조건 | 단절 시 정책 후보 | 재연결·책임 |
|---|---|---|---|
| 이동 점검 | 수집 주기와 이상 발견 허용 시간이 이동·측정·전송 지연을 수용해야 한다. 센서값은 측정 시각을 보존 | 승인된 경로만 로컬로 계속. 중요 경보가 허용 시간을 넘기면 현장 호출 | 점검 누락·중복과 측정 품질 대조. 경보 마감은 보전 담당이 정한다 |
| 배송 | 운송 마감, 수령인 대기, 온도 같은 품질 잔여 시간에서 통신 예산을 배분. 문·층 상태는 진입 직전에 유효해야 한다 | 상태가 확정되지 않은 설비에는 진입 보류. 합의된 대기점이나 사람 처리로 전환 | 화물 위치·소유자·인수를 확인한 뒤 재개. 업무·설비·ROP 공동 계약 |
| 서열 공급 | 라인이 필요로 하는 시각에서 운반·인계·완충 시간을 뺀 값이 통신·복구 예산 | 현장 엣지에서 승인된 순서를 유지하거나 수동 공급. 새 전역 계획 없이 순서를 바꾸지 않는다 | 생산 실적·실물·중복 지시 대조. 결품·순서 판정은 생산 담당 |
| 협업 조작 | 제어 주기·힘·거리·정지 요구는 로봇·셀의 검증된 로컬 제어 조건으로 정한다 | 로컬 인터록에 따라 정지 또는 유지. 원격 완료 신호를 잃으면 재시도 전에 물체 상태 확인 | 치구·파지·공구·품질 확인 뒤 승인. 셀 통합자·로봇·설비 담당 |

[의견] 데이터 종류마다 계약이 다르다.

| 데이터 | 계약에 넣을 것 |
|---|---|
| 명령 | 업무 요청 id와 동작 id, 유효 기한, 접수·실행·완료의 분리, 중복·역순·오래된 명령 처리, 소유권 |
| 상태 | 측정 시각과 수신 시각, 순서·재시작 세대, 최대 허용 나이, "알 수 없음" 값, 마지막 값을 보존할 때의 표시 |
| 영상 | 지연, 프레임 손실, 해상도, 통신량, 개인정보. 원격 조작용이면 조작 허용 기준과 연결 |
| 감사 로그 | 결손 탐지, 지속 저장, 시간 동기, 작업·구성 id, 정정 이력. 재전송 우선순위는 명령과 분리 |

## 6. 검증·한계

- 기술별 역할은 각 명세·문서의 해당 절을 읽어 확인했다. 실제 부하·단절 시험은 하지 않았다.
- 계층 책임표와 작업별 단절 정책은 제안이다. 실제 현장 계약이나 측정값으로 채운 것이 아니다.
- 무선 환경에서 명령·상태 메시지의 허용 지연·손실·로밍 중단 시간을 정한 공개 표준은 이번에도 찾지 못했다(열린 질문 oq-039).

## 8. 남은 질문

- 작업마다 지연·단절·상태 신선도 허용값을 어떻게 정하고 피크·연속 단절·재연결 상황에서 확인하는가? (FR06, 관련 oq-039)
- 설비 상태를 몇 초까지 믿고 통과·배정을 확정하는가? 오래되거나 서로 맞지 않는 상태는 어떻게 처리하는가? (FR05, 관련 oq-034)
- 외부망(WAN)과 현장 무선(WLAN) 단절을 나눠, 클라우드와 끊긴 동안 현장에서 어디까지 계속하는가? (관련 oq-038, oq-206)
- 발표에서 약어로만 나온 통신 방식(PTT)의 정확한 원전은 무엇인가? (FR13)
