# 읽기 가이드

이 위키의 문장에는 상태, 신뢰도, 태그, 각주, 기준일 같은 표기가 붙어 있다. 이 표기는 "이 문장을 얼마나 믿어도 되는가"와 "누가 쓴 문장인가"를 독자가 스스로 판단할 수 있게 하려는 것이다. 이 페이지는 그 표기를 읽는 법, 페이지 유형별 구성, 분류 원문과 에이전트 서술을 구분하는 법, 그리고 스크립트가 자동으로 다시 쓰는 영역이 무엇인지 설명한다.

## 페이지 머리에서 먼저 볼 것

모든 페이지는 프런트매터(YAML 머리말)로 시작한다. 사이트에서는 보이지 않지만 저장소 파일에서는 볼 수 있고, 다음 값이 페이지의 상태를 요약한다.

| 필드 | 뜻 |
|---|---|
| `status` | 페이지 상태. 아래 "상태" 표 참고 |
| `confidence` | 신뢰도(high / medium / low). 내용 검증 에이전트가 부여한다. 시드 페이지에는 없다 |
| `created` / `updated` | 처음 만든 날과 마지막으로 내용을 바꾼 날 |
| `last_run` | 이 페이지를 마지막으로 다룬 실행의 날짜. 이 값으로 `runs/`의 실행 기록을 찾는다 |
| `sources` | 이 페이지 각주에 쓰인 참고문헌 id 목록 |
| `version` | 정수. 갱신마다 1씩 오른다. 이 증가 규칙은 페이지 템플릿의 규약이며 사양서는 `version: 1`만 예시한다 [가정] |
| `related_areas` | 연결된 세부영역 번호 목록 |

본문 첫 줄은 이동 경로("홈 › 대분류 › 세부영역")다. 세부영역 페이지는 그 아래 소속 대분류와 핵심 질문을 상자로 보여 준다.

## 상태

| 상태 | 의미 |
|---|---|
| seed | 원문 정의만 있고 본문이 없음 |
| draft | 스토리텔러 초안, 2차 검증 전 |
| verified | 2차 검증 통과, 게시 대기 |
| published | 게시됨 |
| needs_update | 정정 요청이 있거나 기준일이 오래되어 재검증 필요 |
| deprecated | 대체되었거나 더 이상 유효하지 않음. 대체 페이지 링크 필수 |

구축 직후의 세부영역 페이지는 모두 seed다. 원문 정의와 질문만 있고 나머지 절은 "아직 작성되지 않음"으로 표시된다. 파이프라인이 그 영역을 다루면 draft → verified → published 순으로 올라간다. 게시된 페이지에 정정 요청이 걸리거나 기준일이 오래되면 needs_update가 되고, 다른 페이지로 대체되면 deprecated가 되면서 대체 페이지 링크가 붙는다. 그 링크를 담는 프런트매터 필드 이름 `replaced_by`는 구축자가 정한 것이며, 프런트매터 검사(`pipeline/checks/check_frontmatter.py`)가 deprecated 페이지에 이 필드를 요구한다. [가정]

## 신뢰도

신뢰도(`confidence`)는 페이지 전체에 대한 값이며 내용 검증 에이전트가 부여한다.

| 값 | 기준 |
|---|---|
| high | 핵심 주장이 2개 이상의 독립 출처로 확인됨 |
| medium | 단일 출처이거나 벤더·기사 중심 |
| low | 추정·의견 비중이 높음 |

페이지 열람이 막힌 환경에서 실행된 결과에는 high가 붙지 않는다. 그런 실행에서는 출처를 검색 결과로만 확인했기 때문에 교차 확인이 됐더라도 medium이 상한이다. [가정] 그 경우 출처 각주에 "원문 미열람"이 표시된다.

## 주장 태그

본문의 주장 문장에는 다음 태그 가운데 하나가 붙는다.

| 태그 | 뜻 | 누가 붙이는가 |
|---|---|---|
| `[사실]` | 출처로 확인된 주장. 각주가 함께 붙는다 | 리서치 에이전트가 제안하고 내용 검증 에이전트가 확정 |
| `[추정]` | 근거는 있으나 확인이 부족한 주장. 벤더 주장이 여기에 들어간다 | 위와 같음 |
| `[의견]` | 작성자(에이전트 또는 구축자)의 해석이나 판단 | 위와 같음 |
| `[분류원문]` | 분류 원문 `_source/ROP_SCM_연구분야_분류.md`에서 한 글자도 바꾸지 않고 옮긴 문장이나 표 | 구축 시 부여하며, 에이전트가 원문을 새로 인용할 때도 원문을 그대로 복사해 붙인다. 에이전트는 이미 있는 이 문장을 고치지 않는다 |
| `[가설]` | 중점 연구 트랙에서 검증할 가설. 트랙 개요에 판정 상태(지지 / 부분 지지 / 기각 / 미판정)가 함께 있다 | 트랙 정의에서 부여 |
| `[사용자 실험]` | 사용자가 `experiments/`에 넣은 실험 결과에서 가져온 주장 | 리서치 에이전트가 반영 |

다음은 표기 형식을 보이는 예시이며, 각주 `[^ref-003]`이 그 출처를 가리킨다.

> GS1 EPCIS는 제품·자산의 상태·위치·이동·인계 이벤트를 공유하는 표준이다. [사실][^ref-003]

위키 운영 방식을 설명하는 문장(이 페이지, [에이전트 소개](agents.md), [기여·정정 방법](how-to-contribute.md))에는 태그를 붙이지 않는다. 그 문장들은 외부 세계에 대한 주장이 아니라 이 위키의 규칙 설명이기 때문이다. [가정]

## 태그가 바뀌는 규칙

태그는 고정이 아니다. 검증과 후속 조사에 따라 오르내린다.

- **강등**: 근거가 약한 `[사실]`은 내용 검증 에이전트가 `[추정]`으로 내린다. 근거가 없는 주장은 삭제되거나 열린 질문으로 옮겨진다. 강등된 주장은 주제 페이지의 "검증 노트"에 발견 사항 id와 함께 적힌다.
- **`[추정]`에서 `[사실]`로**: 독립 출처가 확인되면 다음 실행에서 올라갈 수 있다. 벤더 주장은 독립 출처로 확인되기 전까지 `[추정]`에 머문다.
- **`[가설]`과 `[사용자 실험]`에서 `[사실]`로**: 둘 다 내용 검증 에이전트의 판정이 있어야 한다. 사용자가 실험 결과를 넣었다는 것만으로 사실이 되지 않고, 트랙 가설은 마지막 단계에서 지지·부분 지지·기각·미판정으로 판정된다.
- **`[분류원문]`** 은 바뀌지 않는다. 원문이 바뀌지 않는 한 그 문장도 바뀌지 않는다.
- **월간 재검증**: 발행 2년이 지난 표준·수치와 `[사실]` 태그는 매월 첫 실행에서 다시 확인되고, 대체된 것은 페이지가 `needs_update` 또는 `deprecated`가 된다.

## 각주, 기준일, 접근일

수치·사례·표준 내용에는 출처가 각주로 붙는다. 본문에서는 `[^ref-003]` 형식이고, 각주 정의는 페이지 마지막 "참고 자료" 또는 "출처" 절에 다음 형식으로 있다.

```
[^ref-003]: 기관, 제목, 발행일, URL, 접근일
```

- **참고문헌 id**: `ref-001`부터 `ref-010`은 분류 원문 12장의 1~10번에 대응한다(ref-001 ASCM SCOR, ref-002 ISA-95, ref-003 GS1 EPCIS, ref-004 Open-RMF, ref-005 Li 외 Lifelong MAPF, ref-006 Ma 외 MAPD, ref-007 NIST 협업 로봇 성능, ref-008 NIST ARIAC, ref-009 ROS 2 DDS-Security, ref-010 ROS 2 위협 모델). `ref-011`부터는 파이프라인이 새로 확인한 출처다. 출처별 상세 페이지는 [참고문헌](../references/index.md)에 있다.
- **발행일**: 출처가 발행된 날이다. 모르면 "발행일 미확인" 또는 "미확인"으로 쓴다. 지어내지 않는다.
- **접근일**: 에이전트가 그 출처를 실제로 열어 확인한 날이다. 원문을 열지 못한 출처는 접근일 뒤에 "(원문 미열람)"이 붙는다. 이 표시가 있으면 검색 결과의 기관·제목·URL 일치로만 실재를 확인한 것이다.
- **교차 확인**: 수치·사례 가운데 핵심 수치는 2개 이상의 독립 출처로 교차 확인된다. 확인하지 못한 것은 채우지 않고 "미확인"으로 남거나 열린 질문으로 보내진다. 교차 확인된 건수는 주제 페이지의 "검증 노트"에 "교차 확인 n건"으로 적힌다.
- **기준일**: 모든 사실에는 기준일(발행일 또는 확인일)이 있다. 본문에서 "2024년 6월 기준"처럼 쓰거나 각주의 발행일로 대신한다. 오래된 기준일은 그 사실이 지금은 다를 수 있다는 신호이며 월간 재검증의 대상이 된다.
- **직접 인용**: 출처 원문의 직접 인용은 출처당 1회, 짧은 구절만 있다. 나머지는 요약·재서술이다. 출처의 표·그림은 복제하지 않고 필요하면 Mermaid 도식으로 다시 그린다.
- **각주 재사용**: 같은 주장에는 같은 각주 id를 다시 쓴다. 같은 `ref-` id는 위키 어디서나 같은 출처다.

## "벤더 주장" 병기

제조사·솔루션 업체의 기능·성능 주장은 독립 출처로 확인되기 전까지 `[추정]`에 "벤더 주장"을 병기한다. 문장 형태는 `…을 지원한다. [추정] 벤더 주장[^ref-0nn]` 이다. 온톨로지 초안의 적용 예시에 제조사 문서에서 가져온 값을 적을 때도 값마다 `[추정] 벤더 주장`을 병기한다. 벤더 문서는 문서 구조나 정보 형태의 사례로는 인용될 수 있지만, 거기 적힌 수치가 사실로 서술되지는 않는다. 벤더 주장이 독립 출처로 확인되면 다음 실행에서 `[사실]`로 올라갈 수 있다.

## 충돌하는 출처

서로 다른 출처가 충돌하면 에이전트는 한쪽을 고르지 않는다. 둘 다 제시하고 [열린 질문](../open-questions.md)에 올린다. 본문에서 "출처 A는 …이라 하고 출처 B는 …이라 한다"처럼 두 주장이 나란히 있고 열린 질문 링크가 붙어 있으면 이런 경우다.

## "미확인"과 빈 절

확인하지 못한 것은 채우지 않는다. 본문에서 "미확인"은 조사했으나 확인하지 못했다는 뜻이고, 절 제목 아래 "아직 작성되지 않음"은 그 절을 아직 다루지 않았다는 뜻이다. 둘 다 빈 곳을 그럴듯한 문장으로 메우지 않는다는 규칙의 결과다. 어느 절이 비어 있는지는 [운영 지표](../metrics.md)의 영역별 상태 분포로 볼 수 있다.

"빠짐없이", "완전", "모든 기능" 같은 표현은 측정 결과(커버리지 지표)가 있을 때만 쓰인다. 그 전에는 목표로만 서술된다. 중점 연구 트랙의 컨셉 문장에 있는 "빠짐없이"는 사용자가 정의한 문장이므로 그대로 두되, 에이전트의 주장에는 쓰지 않는다.

## 원문 정의와 에이전트 서술을 구분하는 법

이 위키에는 두 종류의 문장이 섞여 있다. 분류 원문(`_source/ROP_SCM_연구분야_분류.md`)에서 그대로 옮긴 문장과, 에이전트 또는 구축자가 쓴 문장이다. 구분하는 방법은 다음과 같다.

**1. `[분류원문]` 태그.** 원문에서 옮긴 문장은 끝에 `[분류원문]`이 붙는다. 굵게 표시와 원문의 `[1]`~`[10]` 번호까지 한 글자도 바꾸지 않는다. 표를 옮겼을 때는 표 바로 아래 줄에 `[분류원문]`만 따로 둔다. 예를 들어 다음은 원문 1장의 정의 문장이다.

> SCM 관점에서 ROP는 **주문·물류·생산 계획을 로봇과 현장 설비의 실제 행동으로 연결하고, 결과를 다시 업무 시스템에 반영하는 실행 플랫폼**으로 볼 수 있다. [분류원문]

**2. "원문 주석" 인용 블록.** 세부영역 페이지의 2번 절 아래에는 원문이 그 영역에 덧붙인 설명이 `> 원문 주석:`으로 시작하는 인용 블록에 들어 있다. 예를 들어 7. 화물·재고·자산 식별과 추적 페이지에는 다음이 있다.

> 원문 주석: **7번은 SCM 관점에서 특히 빠뜨리기 쉽다.** 로봇 위치를 추적하는 것과 화물의 위치·인계 책임을 추적하는 것은 다르다. GS1 EPCIS는 제품·자산의 상태, 위치, 이동, 인계에 관한 이벤트를 공유하는 참고 표준이다. [3] [분류원문]

이 블록 안의 `[3]`은 원문 12장 참고 자료의 3번을 가리키며, 이 위키의 참고문헌 `ref-003`에 해당한다. 블록 바로 아래의 "원문의 [3]은 참고문헌 ref-003에 해당한다" 같은 문장은 구축자가 덧붙인 안내이지 원문이 아니다.

**3. 번호만 있는 표기.** 원문은 "7번", "27번의 AI"처럼 번호만으로 영역을 부르기도 한다. 그런 표기가 있으면 원문 문장이다. 에이전트와 구축자의 서술은 항상 "7. 화물·재고·자산 식별과 추적"처럼 번호와 이름을 함께 쓴다.

**4. 원문이 있는 자리.** 원문은 `[분류원문]` 태그가 붙은 문장과 표에만 있다. 대표적인 자리는 홈, 소개 4페이지([SCM 관점의 ROP란 무엇인가](what-is-rop.md), [ROP가 직접 소유할 범위와 외부 연계 경계](scope-boundary.md), [SCM 관점의 연구 시작 방법](research-method.md), [논의한 아이디어의 연구영역 매핑](idea-mapping.md)), 대분류 페이지의 1~4번 절, 세부영역 페이지의 1·2번 절과 원문 주석 블록, 참고문헌 페이지의 원문 항목이다. 세부영역 페이지 상단의 소속 대분류 상자, 용어집 항목, 표준·프레임워크 목록, 트랙 개요·온톨로지 초안·트랙 로그·단계 페이지에도 원문을 인용한 자리가 있다. 태그가 없는 본문은 모두 에이전트 또는 구축자의 서술이며 주장마다 태그와 각주가 붙는다.

**5. 원문은 바뀌지 않는다.** 대분류·세부영역의 명칭·번호·정의·질문은 변경·축약·병합되지 않는다. 퍼블리셔가 매 실행마다 28개 세부영역 페이지의 `[분류원문]` 문장을 원문과 글자 단위로 대조한다. 새 세부영역이 필요해 보이면 분류를 바꾸지 않고 [열린 질문](../open-questions.md)에 "분류 확장 제안"으로만 기록한다.

트랙의 컨셉 문장과 온톨로지 초안 v0의 개념은 또 다른 경우다. 컨셉은 사용자가 정의한 문장 그대로이고, 온톨로지 초안 v0는 5. 로봇 능력·작업 온톨로지의 원문 정의에서 가져온 개념만으로 시작해 "`[분류원문]` 기반 `[가정]`"으로 표시된다.

## 자동 갱신 영역

일부 페이지에는 퍼블리셔 스크립트가 매 실행마다 다시 쓰는 부분이 있다. 그 부분은 저장소 파일에서 다음 두 주석 사이에 있다.

```
<!-- auto:<key>:start -->
…
<!-- auto:<key>:end -->
```

사이트에서는 주석이 보이지 않는다. 마커 사이의 내용은 `data/*.json`이나 실행 산출물에서 만들어지므로 사람이 손으로 고쳐도 다음 실행에서 덮어써진다. 마커 밖의 본문은 스크립트가 건드리지 않는다.

| 위치 | 자동 갱신되는 것 |
|---|---|
| 홈 | 진행 중인 중점 연구 트랙 현황, 최근 업데이트 5건 |
| 대분류 페이지 | 세부 연구영역 표 전체(원문 열은 원문 그대로 다시 그리고 현재 상태 열을 갱신), 최근 업데이트 |
| 세부영역 페이지 | 12. 최근 업데이트 |
| 트랙 개요 | 단계 진행 현황, 최근 실행 |
| 질문 백로그, 온톨로지 초안 | 백로그 표, 버전 이력 |
| 트랙 로그 | 실행별 기록 |
| 참고문헌 항목 페이지 | 인용된 페이지 목록 |
| 열린 질문, 변경 이력, 물류 흐름 매트릭스, 운영 지표 | 본문 표 전체 |
| 용어집·참고문헌·표준·주제·로그 색인 | 목록 |

따라서 이 부분의 내용은 어느 실행이 쓴 것인지 실행 id로 추적할 수 있고, 직접 고치고 싶은 것이 있으면 페이지가 아니라 정정 요청이나 원천 데이터를 고쳐야 한다. 방법은 [기여·정정 방법](how-to-contribute.md)에 있다.

## 항목 호칭과 표기

- 본문은 평서체("~이다/~한다")와 짧은 단락으로 쓴다. 마케팅 표현과 근거 없는 단정은 쓰지 않는다.
- 대분류와 세부영역은 항상 번호와 이름을 함께 쓴다. "7. 화물·재고·자산 식별과 추적", "B. 공통 정보·환경 모델". "B-7", "7번"처럼 번호만 쓰지 않는다. 도식과 표 안에서도 같다.
- 물류 흐름 단계는 입고, 적치, 보충, 피킹, 포장, 출하, 반품이고, 여섯 항목은 시작 조건, 작업 대상, 수행 자원, 제약, 완료·인계, 예외·성과다. 현장 시나리오와 [물류 흐름 매트릭스](../flow-matrix.md)가 이 축을 쓴다.
- 전문용어는 첫 등장 시 영문을 병기하고, 약어는 첫 등장 시 풀어 쓴다. 정의는 [용어집](../glossary/index.md)에 있다.
- 날짜는 YYYY-MM-DD(Asia/Seoul), 실행 id는 YYYY-MM-DD-NN, 열린 질문 id는 oq-001부터, 트랙 백로그 질문 id는 q<단계>-<두 자리>(예 q1-01), 정정 요청 id는 corr-001부터다.
