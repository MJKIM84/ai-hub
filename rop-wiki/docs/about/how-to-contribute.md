# 기여·정정 방법

이 위키의 본문은 에이전트가 쓰지만, 무엇을 먼저 조사할지, 어떤 문장이 틀렸는지, 검증에 걸린 산출물을 어떻게 할지, 실험 결과를 어떻게 넣을지, 에이전트 규칙을 어떻게 바꿀지는 사람이 정한다. 이 페이지는 그 다섯 가지 개입 방법을 절로 나누어 설명한다. 아래 표는 빌드 사양서 7.4의 개입 지점을 기준으로 한 여섯 행이며, 트랙 백로그 질문(`track_questions`)은 우선순위 지정 절에서 함께 다룬다. 어느 방법이든 페이지 본문을 직접 고치는 대신 정해진 파일에 요청을 적는 방식이다. 그래야 에이전트가 다음 실행에서 근거를 확인하고, 처리 결과가 [변경 이력](../changelog.md)에 남는다.

## 무엇을 어디에 쓰는가

| 하고 싶은 일 | 쓰는 곳 | 언제 반영되는가 |
|---|---|---|
| 특정 영역·주제·질문을 먼저 조사하게 하기 | `config/priority.yaml` | 다음 대상 선정에서 순환보다 우선한다 |
| 트랙 백로그에 질문을 넣고 우선순위 올리기 | `config/priority.yaml`의 `track_questions` | 다음 트랙 실행에서 가장 먼저 다룬다 |
| 틀린 문장·오래된 사실·잘못된 태그 고치기 | `inbox/corrections.md` | 다음 실행의 검증 항목에 포함되고 결과가 변경 이력에 남는다 |
| 검증에 걸려 보류된 산출물 처리하기 | `runs/parked/` | 재투입하면 걸렸던 단계부터 다시 실행된다 [가정]. 재투입 절차는 파이프라인 절차서(`pipeline/RUN.md`)를 따른다 |
| 직접 수행한 실험 결과 넣기 | `experiments/<날짜>-<이름>/` | 다음 트랙 실행에서 `[사용자 실험]` 태그로 반영된다 |
| 에이전트의 규칙 바꾸기 | `agents/*.md` | 버전을 올리고 변경 이력에 기록한 뒤, 다음 실행부터 적용된다 |

## 우선순위 지정: `config/priority.yaml`

대상 선정은 기본적으로 순환 규칙을 따른다. 1주기에는 세부영역 번호순, 2주기부터는 점수(마지막 갱신 경과일 + 열린 질문 수 + 비어 있는 매트릭스 칸 수 + 우선 가중치 − 최근 7일 감점)로 고른다. `config/priority.yaml`에 적은 항목은 이 순환보다 우선한다.

네 가지를 지정할 수 있다.

| 키 | 항목 필드 | 뜻 |
|---|---|---|
| `areas` | `area_no`, `weight`, `reason` | 세부영역을 먼저 다루게 한다. `weight`는 선정 점수에 더해지는 가중치이고 `reason`은 로그에 남는 지정 사유다 |
| `topics` | `title`, `area_no`, `weight` | 특정 주제로 주제 조사를 실행하게 한다. `area_no`는 주 연구영역이다 |
| `questions` | `question`, `area_no` | 답을 찾게 할 질문이다. 리서치 에이전트의 조사 질문에 포함된다 |
| `track_questions` | `track`, `stage`, `question`, `priority` | 트랙 백로그에 넣을 질문이다. 제기 근거가 "사용자"로 기록되고 다음 트랙 실행에서 사용자 지정 질문으로 가장 먼저 처리된다 |

예시는 다음과 같다. 항목이 없는 키는 빈 목록(`[]`)으로 둔다.

```yaml
# config/priority.yaml — 사용자가 지정하는 우선 영역·주제·질문. 비어 있으면 순환 규칙만 따른다.
areas:
  - area_no: 7            # 7. 화물·재고·자산 식별과 추적
    weight: 10            # 대상 선정 점수에 더하는 가중치
    reason: "인계 확인 사례가 부족하다"
topics:
  - title: "팔레트 인계 확인에 EPCIS 이벤트를 쓰는 방법"
    area_no: 7            # 주 연구영역: 7. 화물·재고·자산 식별과 추적
    weight: 8
questions:
  - question: "로봇 도착과 실제 팔레트 인계를 어떤 이벤트로 구분해 기록하는가?"
    area_no: 7
track_questions:
  - track: manual-capability-ontology
    stage: 1              # 질문을 넣을 단계 번호(1~7)
    question: "산업 상호운용 규격의 팩트시트는 적재 제약을 어떤 필드로 기술하는가?"
    priority: high        # high | normal | low [가정]
```

몇 가지 유의점이 있다.

- `area_no`는 1~28의 번호다. 사람이 읽기 쉽도록 주석에 영역 이름을 함께 적는 것이 좋다.
- 지정한 항목이 처리되면 목록에서 지워도 된다. 지우지 않으면 최근 7일 안에 다룬 항목은 건너뛰고(`config/rotation.yaml`의 `priority.skip_if_targeted_within_days`), 그 기간이 지나면 다시 우선된다. 같은 항목만 매일 반복 선정되지 않게 하려는 규칙이다. [가정]
- 우선 지정은 조사 대상을 정할 뿐, 검증 규칙을 바꾸지 않는다. 우선 지정된 주제라도 출처가 확인되지 않으면 게시되지 않는다.
- 하루 예산(신규 주제 페이지 1개, 기존 페이지 갱신 2개)은 그대로 적용된다. 우선 항목이 예산보다 많으면 여러 날에 걸쳐 처리된다.

## 정정 요청: `inbox/corrections.md`

게시된 문장이 틀렸거나, 출처가 오래됐거나, 태그가 과하거나(예: 벤더 주장이 `[사실]`로 적힘), 링크가 깨졌거나, 다른 영역에 있어야 할 내용이면 `inbox/corrections.md`에 정정 요청을 적는다. 한 요청은 `## corr-NNN` 제목으로 시작하는 블록 하나이며, 페이지 경로, 문제 문장, 근거, 요청일, 요청자, 상태를 적는다. 정확한 형식과 예시, 거부되는 경우는 [정정 요청 안내](../corrections.md)에 있다.

처리 시점과 흐름은 다음과 같다.

1. 다음 실행의 대상 선정에서 정정 요청이 걸린 페이지가 있으면 그 페이지의 갱신을 당일 작업에 포함한다.
2. 리서치 에이전트가 요청을 조사 질문에 넣고, 원 주장이 틀렸으면 바로잡는 근거를, 맞았으면 확인 근거를 찾는다.
3. 내용 검증 에이전트가 1차 검증 항목 11 "정정 요청 반영 여부"로 확인한다.
4. 스토리텔러 에이전트가 페이지에 반영한다.
5. 퍼블리셔가 [변경 이력](../changelog.md)에 기록하고 요청의 상태를 `applied`로 바꾼다. 검증이 반영하지 않기로 판정한 요청은 `rejected`가 되고 사유가 남는다. [가정]

정정 요청으로 할 수 없는 것도 있다. 분류 원문의 명칭·번호·정의·질문은 정정 대상이 아니다. 새 세부영역이 필요하다는 의견은 [열린 질문](../open-questions.md)에 "분류 확장 제안"으로만 남는다. 새로 조사할 주제는 정정이 아니라 `config/priority.yaml`에 적는다.

## 보류 산출물 검토: `runs/parked/`

1차 검증에서 반려가 재조사 2회 뒤에도 이어지거나, 2차 검증에서 불통과가 재작성 2회 뒤에도 이어지면 그날의 실행 폴더 `runs/<실행 id>/`가 통째로 `runs/parked/<실행 id>/`로 옮겨진다. 스키마 불일치가 재실행 뒤에도 남을 때도 같다. 보류된 산출물은 위키에 반영되지 않았고, 사람이 보기 전까지 그대로 남는다.

**무엇이 들어 있는가.** `target.json`(무엇을 다루려 했는가), `research.json`·`research.md`(브리프), `verification.json`·`verification.md`(1차 판정과 사유), 2차까지 갔다면 `verification2.json`·`verification2.md`와 `pages/`·`pages.json`(스토리텔러 결과), `prompts/`(에이전트에 준 프롬프트), `log.md`(어디까지 진행됐고 왜 걸렸는지), `summary.json`(요약 수치)이다.

**어떻게 검토하는가.** `log.md`에서 걸린 단계와 사유를 먼저 보고, `verification.md`의 반려 사유·수정 지시를 읽은 뒤, `research.md` 또는 `pages/`에서 실제 산출물을 본다. 보통 다음 셋 중 하나로 판단된다.

- 조사 자체가 어려운 영역이다 — 출처가 드물거나 유료다. `config/priority.yaml`에 질문을 더 구체적으로 적거나, 관련 자료를 [열린 질문](../open-questions.md)에 힌트로 남긴 뒤 재투입한다.
- 검증 기준이 맞았고 산출물이 부족하다 — 폐기하고 순환에 맡긴다.
- 검증이 과하게 엄격했거나 규칙 해석이 어긋났다 — `agents/` 규칙을 손볼지 검토한다. 이 경우에도 사용자 확인 없이 규칙을 완화하지는 않는다.

**재투입.** `runs/parked/<실행 id>/`를 `runs/<실행 id>/`로 되돌리고 실행 스크립트를 재투입 옵션으로 실행한다. 이 페이지는 `pipeline/run_daily.sh --resume <실행 id>`를 가정하며, 실제 파일 이름(확장자)과 옵션 이름은 파이프라인 절차서 `pipeline/RUN.md`를 따른다. [가정] 걸렸던 단계부터 다시 진행된다. 재투입 전에 `config/priority.yaml`이나 `inbox/corrections.md`를 고쳐 두면 재실행에서 그 입력이 반영된다.

**폐기.** `runs/parked/<실행 id>/DISCARDED` 파일을 만들고 그 안에 날짜와 사유를 한 줄 적는다. 폴더는 기록으로 남기되 더 이상 검토 대상이 아니라는 표시다. [가정]

같은 영역이 3회 연속 보류되면 대상 선정에서 그 영역이 제외되고 사용자 검토 요청이 [열린 질문](../open-questions.md)에 올라간다. 검토를 마친 뒤 그 영역을 다시 다루게 하려면 `config/priority.yaml`의 `areas`에 지정한다. [가정] 보류 건수는 [운영 지표](../metrics.md)에 집계된다.

## 실험 결과 입력: `experiments/`

중점 연구 트랙의 실험은 사용자가 직접 수행한다. 스토리텔러 에이전트는 단계 3·5·7에서 실험 계획을 [실험](../tracks/manual-capability-ontology/experiments.md) 페이지에 제안하고, 사용자는 결과를 저장소의 `experiments/` 폴더에 넣는다.

- 폴더 이름은 `experiments/<날짜>-<이름>/`이다. 예: `experiments/2026-10-15-amr-manual-extraction/`. 날짜는 YYYY-MM-DD, 이름은 영문 소문자와 하이픈이다.
- 폴더에는 `README.md`와 데이터 파일을 둔다. `README.md`에는 목적, 방법, 결과 요약을 적고, 어느 트랙·단계·질문(또는 실험 계획)에 대한 결과인지 밝힌다. 수치에는 측정 조건을 함께 적는다.
- 다음 트랙 실행에서 리서치 에이전트가 이 폴더를 읽어 `[사용자 실험]` 태그로 반영한다. `[사실]`로 올라가려면 내용 검증 에이전트의 판정이 필요하다. 실험 결과가 기존 발견 사항이나 온톨로지 초안과 충돌하면 출처 충돌과 같이 둘 다 제시되고 열린 질문에 올라간다.
- 제조사 문서 원문을 통째로 넣지 않는다. 문서 구조나 정보 형태의 사례로 필요한 부분만 짧게 발췌하고 출처를 적는다. 개인정보나 비공개 자료도 넣지 않는다.

`README.md` 서식과 자세한 규칙은 저장소의 `experiments/README.md`에 있다.

## 에이전트 규칙 변경: `agents/`

에이전트의 행동은 `agents/shared-rules.md`(공통 규칙)와 `agents/researcher.md`, `agents/verifier.md`, `agents/storyteller.md`(역할별 규칙)가 정한다. 규칙을 바꾸는 절차는 다음과 같다.

1. 해당 파일 머리의 `version` 값을 올리고 날짜를 적는다(예: `version: 1.1 (2026-10-01)`).
2. 무엇을 왜 바꿨는지 [변경 이력](../changelog.md)에 기록한다. 변경 이력의 원천은 `data/changelog.json`이므로 거기에 항목을 추가한다. [가정]
3. 다음 실행부터 새 규칙이 적용된다. 실행마다 사용된 프롬프트는 `runs/<실행 id>/prompts/`에 남으므로 어느 실행이 어느 버전으로 돌았는지 추적할 수 있다.

사용자 확인 없이 규칙을 완화하는 변경(예: 출처 없이 써도 된다, 벤더 주장을 사실로 써도 된다)은 하지 않는다. 분류 원문 보호, 사실 표기, 검증 통과 없는 게시 금지는 어떤 변경에서도 유지된다.

## 페이지를 직접 고치고 싶을 때

가능하면 정정 요청을 쓴다. 직접 고치면 근거가 검증되지 않고 변경 이력에도 남지 않기 때문이다. 그래도 직접 고쳐야 한다면 다음을 지킨다.

- `[분류원문]` 문장과 대분류·세부영역의 명칭·번호·정의·질문은 고치지 않는다. 퍼블리셔의 원문 보호 검사가 실패하면 그 뒤의 실행이 반영되지 않는다.
- `<!-- auto:<key>:start -->`와 `<!-- auto:<key>:end -->` 사이는 고치지 않는다. 다음 실행에서 덮어써진다.
- 프런트매터의 `updated`와 `version`을 올리고, 절 제목과 순서를 바꾸지 않는다.
- 고친 뒤 `pipeline/checks/run_all.sh`로 프런트매터·링크·원문 보호 검사를 통과하는지 확인한다.
