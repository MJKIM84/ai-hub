# 실험

이 페이지는 중점 연구 트랙 [매뉴얼 기반 로봇 기능 온톨로지](index.md)에서 스토리텔러 에이전트가 제안한 실험 계획과, 사용자가 직접 수행해 저장소의 `experiments/` 폴더에 넣은 실험 결과의 요약을 모은다. 선택 페이지이며, 실험이 없어도 트랙은 진행된다.

## 실험 규칙(8.2)

- **실험은 사용자가 직접 수행한다.** 에이전트는 실험을 수행하지 않는다. 에이전트가 하는 일은 계획을 제안하고, 사용자가 넣은 결과를 읽어 반영하는 것이다.
- **계획은 스토리텔러 에이전트가 단계 3·5·7에서 제안한다.** 단계 3(비정형 문서에서 온톨로지를 추출하는 방법 조사)에서는 추출 방법을 실제 문서에 적용해 보는 실험을, 단계 5(완전성과 정확성을 검증하는 방법 조사)에서는 커버리지·정확도를 측정하는 실험을, 단계 7(ROP 활용 시나리오 종합과 가설 판정)에서는 가설 판정에 필요한 실험을 제안한다. 다른 단계에서 필요하면 제안할 수 있으나 필수는 아니다. [가정]
- **결과는 `experiments/<날짜>-<이름>/`에 넣는다.** 다음 트랙 실행에서 리서치 에이전트가 이 폴더를 읽어 발견 사항으로 만들고, 페이지에서는 `[사용자 실험]` 태그로 표시된다.
- **`[사용자 실험]`은 `[사실]`이 아니다.** `[사실]`로 올라가려면 내용 검증 에이전트의 판정이 필요하다. 사용자가 결과를 넣었다는 것만으로 사실이 되지 않는다.
- **충돌은 숨기지 않는다.** 실험 결과가 기존 발견 사항이나 [능력 온톨로지 초안](ontology-draft.md)과 충돌하면 출처 충돌과 같이 둘 다 제시되고 [질문 백로그](question-backlog.md)(또는 위키의 [열린 질문](../../open-questions.md))에 올라간다.
- **"빠짐없이"는 측정 결과가 있을 때만.** 커버리지 같은 지표를 실제로 측정했다면 수치와 측정 조건을 적는다. 측정하지 않았으면 "빠짐없이", "완전", "모든 기능" 같은 표현을 쓰지 않는다.

## 계획 제안 형식

스토리텔러 에이전트는 실험 계획을 아래 표 형식으로 이 페이지의 "제안된 실험 계획" 절에 추가한다. [가정]

| 항목 | 내용 |
|---|---|
| 계획 번호 | `E<단계>-<두 자리>` 형식(예 `E3-01`). 제안 순서대로 매기고 재사용하지 않는다 |
| 제안 단계 | 3 / 5 / 7 중 하나(번호와 이름을 함께 쓴다) |
| 답하려는 질문 | 질문 백로그의 id(여러 개면 쉼표 구분)와 관련 가설 |
| 목적 | 무엇을 알아내려 하는가. 한두 문장 |
| 방법 | 대상 문서·기종(공개 문서면 이름·버전·URL), 사용할 도구, 절차. 다른 사람이 재현할 수 있을 만큼 |
| 측정 지표와 조건 | 무엇을 어떻게 세는가(예: 커버리지의 분모·분자 정의, 정답 판정 기준) |
| 필요한 자료·예상 비용 | 공개 문서, 도구, 사람 검토 시간 등 |
| 제안한 실행 id | 계획을 제안한 트랙 실행의 id |
| 상태 | 제안됨 / 수행 중 / 결과 반영됨 / 철회 |

## 사용자 결과 입력 형식

사용자는 실험을 마친 뒤 저장소의 `experiments/<날짜>-<이름>/` 폴더를 만들고 `README.md`와 데이터 파일을 넣는다. 자세한 규칙과 서식은 저장소의 `experiments/README.md`와 [기여·정정 방법](../../about/how-to-contribute.md)의 "실험 결과 입력" 절에 있다. 핵심은 다음과 같다.

- 폴더 이름은 `YYYY-MM-DD-<slug>`이다. 날짜는 실험을 수행한 날(또는 결과를 넣은 날), slug는 영문 소문자·숫자·하이픈이다. 예: `experiments/2026-10-15-amr-manual-extraction/`.
- `README.md`는 필수이며 머리에 트랙(`manual-capability-ontology`), 단계, 답하려는 질문 id, 실험 계획 번호(또는 "자체 설계"), 수행일, 수행자, 이전 실험을 적고, 본문에 목적 / 방법 / 결과 요약 / 한계 / 데이터 파일 절을 둔다.
- 결과 요약에는 수치와 측정 조건을 함께 적는다. 예를 들어 커버리지를 적을 때는 무엇을 분모로 세었는지, 무엇을 정답으로 판정했는지를 밝힌다.
- 제조사 문서 원문을 통째로 넣지 않는다. 문서 구조나 정보 형태의 사례로 필요한 부분만 짧게 발췌하고 출처(문서 이름, 버전, 페이지)를 적는다. 개인정보, 비공개 계약 자료, 고객 현장의 식별 정보도 넣지 않는다.
- 한 번 넣은 폴더는 고치지 않는다. 같은 실험을 다시 하면 새 날짜의 폴더를 만들고 `README.md`에 이전 폴더를 적는다.

반영 흐름은 다음과 같다. 다음 트랙 실행에서 스크립트가 폴더를 리서치 에이전트의 입력에 넣는다 → 리서치 에이전트가 결과를 발견 사항(태그 `사용자 실험`)으로 만든다 → 내용 검증 에이전트가 방법·측정 조건이 적혀 있는지와 기존 발견 사항·온톨로지 초안과의 충돌을 본다 → 스토리텔러 에이전트가 단계 페이지와 이 페이지의 "사용자 실험 결과 요약" 절에 `[사용자 실험]` 태그로 반영하고, 온톨로지 초안 변경이 필요하면 근거 발견 사항 id와 함께 제안한다 → 결과는 [트랙 로그](log.md)와 [변경 이력](../../changelog.md)에 남는다.

## 제안된 실험 계획

현재 제안된 실험 없음. 단계 3·5·7의 트랙 실행에서 스토리텔러 에이전트가 계획을 제안하면 여기에 추가된다.

## 사용자 실험 결과 요약

아직 없음. 사용자가 `experiments/`에 결과를 넣고 다음 트랙 실행이 반영하면, 실험마다 폴더 이름, 답한 질문 id, 결과 요약(수치·측정 조건), 반영된 페이지 링크, 검증 판정을 여기에 요약한다.
