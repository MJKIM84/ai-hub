## 3. 본문

로봇 인터페이스가 제공하는 변경 수단은 주문 갱신·일시정지·취소·중단·되감기 정도이므로, 우선순위 변경 규칙과 상위 지시의 번역은 ROP 쪽 대기열·재계획 로직이 맡아야 할 것으로 보인다. [추정][^ref-031][^ref-125] 2026-09-25 실행까지의 내용: [23. 업무 시스템 연동 — 대표 접근법과 기술 (2026-09-25)](2026-09-25-area01-s6.md) — 그 페이지에 VDA 5050 변경 수단과 Open-RMF 중단·되감기 같은 기존 확인 내용이 있다.

아래는 이번 조사에서 확인한 수단과 연구 접근이다.

### 2026-10-11 보강: 접수 응답과 실제 진행·취소 결과의 분리

Open-RMF rmf_api_msgs 의 작업 배정 응답 스키마(커밋 e9b7630 고정본, 2026-10-11 확인)는 성공이면 success 와 작업 상태(task_state 를 따르는 state)를 필수로 요구하고, 실패면 실패 이유를 담는 errors 배열을 둔다. [사실][^ref-1441] 같은 저장소의 취소 응답 스키마는 자체 필드 없이 simple_response 를 참조하며, simple_response 는 성공이면 success=true 만, 실패면 success=false 와 errors 를 필수로 요구한다. [사실][^ref-1445][^ref-1446] 따라서 Open-RMF 의 취소 응답은 요청 처리의 성패만 알리고, 작업이 실제로 멈춰 canceled 상태가 됐는지는 작업 상태(task_state)를 따로 관측해 확인해야 할 것으로 보인다. [추정][^ref-1445][^ref-1446] 응답과 실제 정지의 시간 관계와 중복 요청의 효과는 미확인이다.

SAP Warehouse Robotics(SAP BTP 위에 만든 제품으로 SAP EWM 과 구별된다)의 [플릿 관리 시스템](../../glossary/fleet-management-system.md)(Fleet Management System, FMS) 연동 API 문서는 이 API 를 폐기(Deprecated)로 표시한다(LATEST URL, 확보본 2024-07-10 기준). [추정] 벤더 주장[^ref-1447][^ref-1449] 아래 세 규칙은 모두 이 폐기 표시된 API 의 것이며, SAP 의 현재 권장 연동 경로의 계약으로 일반화하지 않는다(현재 경로의 계약은 미확인).

- FMS 는 요청에 대한 응답을 관련 콜백 메서드 호출보다 먼저 돌려줘야 한다(요청 → 응답 → 콜백 순서). [추정] 벤더 주장[^ref-1447]
- 취소에 성공하면 Update Robot Task Status 로 taskStatus 를 CANCELLED 로 알리고, 취소할 수 없으면 별도 메서드 Update Robot Task Cancelation Status 로 알린다. [추정] 벤더 주장[^ref-1447]
- 공통 메시지는 UUID 형식의 messageId 를 필수로 두고 작업은 이와 별도인 robotTaskId 로 가리켜 메시지 식별과 작업 식별을 나누며, 중복 제거나 재시도 보장 같은 운영 보장은 문서에 없다. [추정] 벤더 주장[^ref-1447]

구축자 의견: 업무 시스템–관제 인터페이스를 비교할 때는 접수 응답, 진행 통지(콜백·상태), 취소 결과, 업무 확정을 따로 보는 것이 좋아 보인다. [의견][^ref-1447][^ref-1441][^ref-1445]

### 업무 '취소'를 로봇 명령으로 옮기기 전의 상태 확인

구축자 의견: 업무 쪽 '취소'를 로봇 명령 하나로 옮기기 전에 작업의 현재 상태(시작 전·실행 중·종료 후), 지울 기록과 남길 이력, 실행 종료 뒤 후처리 여부를 먼저 정해야 할 것으로 보이며, 그 근거는 OPC UA for ISA-95 Job Control 이 시작 전 취소·실행 중 정지·완료 뒤 종결을 서로 다른 메서드와 상태로 둔다는 점이다(4절). [의견][^ref-131] 이 상태들과 VDA 5050·Open-RMF 상태 사이의 표준 매핑은 확인하지 못했다(oq-020).

### 우선순위 변경 허용 범위: 업무 시스템 쪽 규칙(연계 대상)

우선순위 변경을 언제 허용하고 대기열을 어떤 순서로 정렬할지는 아래처럼 연계 대상인 상위 업무 시스템(WMS) 쪽에서 정하는 규칙이다.

- Oracle WMS Cloud 26c REST API 의 작업 우선순위 변경 API 는 Ready·Held·Created 상태인 작업의 우선순위만 바꿀 수 있다고 명시한다. [추정] 벤더 주장[^ref-1448]
- 같은 API 는 외부 시스템이 다른 작업의 긴급도에 따라 우선순위를 바꿀 수 있게 하되, Task/Change task priority 권한이 켜져 있을 때만 쓰게 한다. [추정] 벤더 주장[^ref-1448]
- SAP Warehouse Robotics 의 integration services 경로 문서(판 2308 기준)는 로봇 배정 최적화를 켜지 않으면 로봇이 속한 자원 그룹의 큐 순서를 따르고(첫 큐를 끝내야 다음 큐), 큐 안의 창고 오더를 latest starting date(LSD) 순으로, LSD 가 없으면 생성 시각 순으로 정렬한다고 설명하며, 이 경로는 위 FMS API 와 다른 연동 경로다. [추정] 벤더 주장[^ref-1449]

구축자 의견: ROP 쪽에서는 업무 시스템이 허용해 바꾼 우선순위를 받되, 변경 가능 여부를 업무 작업의 상태와 로봇 실행 단계에 대해 따로 검사하고, 대기열 재정렬과 진행 중 작업 선점은 별도 정책으로 두는 것이 좋아 보인다. [의견][^ref-1448][^ref-1449] 진행 중 Open-RMF 작업의 재정렬 방법과 업체 간 우선순위 숫자의 대응은 미확인이다(oq-019).

### 업무 객체 해석 계층

SAP Architecture Center 의 참조구조 'Warehouse Pick & Place with Embodied AI Robotics'(2026-05-12 갱신)는 이송 오더를 만들고 관리하지만 물건을 집지는 못하는 디지털 창고 AI 에이전트와 구별해, 체화(Embodied) AI 에이전트의 세 가지 주요 skill 가운데 하나로 업무 객체의 의미 이해(WMS 데이터 속성, 예를 들어 주문 우선순위·취급 요건이 물리 작업 실행에 뜻하는 바)를 든다. [추정] 벤더 주장[^ref-1452] 이 영역에서는 이를 업무 객체를 로봇 작업 문맥으로 옮기는 해석 계층의 근거로만 보고, 로봇의 물리 작업 수행은 연계 대상으로 [44. 로봇 기반 모델·언어 모델 계획](../../categories/ai-and-learning/robot-foundation-models-and-llm-planning.md)에서 다룬다. 개념검증 사례는 5절의 물류창고 사례(Bosch·Aimbo)에 있다.

### 모델 컨텍스트 프로토콜(MCP) 같은 새 접점의 실제 범위

NVIDIA Isaac Mission Dispatch README(커밋 56455eb 고정본)의 갱신 표는 2026-03 에 Mission Dispatch MCP 추가를, 2026-08 에 VDA5050 3.0 지원과 generic action node 추가를 기록한다. [사실][^ref-1341] 같은 커밋의 Mission Dispatch [모델 컨텍스트 프로토콜](../../glossary/model-context-protocol.md)(Model Context Protocol, MCP) 서버는 도구 11개(로봇 상태·미션 상태·미션 중 로봇·유휴 로봇·플릿 요약·로봇 건강 점검·미션 큐·최근 실패 조회, 연결 시험, 로봇 등록, 좌표 이동 미션 전송)를 등록하고 미션 취소 도구는 두지 않는 것으로 보이나, 공개 코드의 파일 경로가 출처에 기록되지 않아 검증에서 다시 확인하지 못했다. [추정][^ref-1341] 이 서버의 이동 미션 처리는 경유점 하나짜리 route 미션 트리와 timeout·deadline 을 담아 Mission Dispatch REST API 의 mission 경로로 POST 하는 것으로 보이나, 이 역시 코드 파일 경로가 출처에 기록되지 않아 검증에서 다시 확인하지 못했다. [추정][^ref-1341]

robotmcp 의 demos-ros-mcp-server 예제 1 README(커밋 edbc642 고정본)는 Ubuntu 22.04·ROS 2 Humble·Ignition Gazebo Fortress 에서 ROS-MCP 서버로 창고 시뮬레이션 속 Tugbot 1대를 자연어로 이동시키고 라이다·주행거리 센서와 위치를 조회하는 예시를 설명하며, 업무 시스템 연동은 다루지 않는다. [사실][^ref-1454]

구축자 의견: MCP 를 업무 요청의 접점으로 평가할 때는 공개 코드가 주는 도구 범위(조회·등록·좌표 이동)와 업무 요구(주문 id 대응·허용 상태 검사·실행 전 승인·결과 대조·취소)를 따로 확인해야 하며, 공개 코드의 존재를 다사업자 WMS 주문·재고 처리의 운영 검증으로 볼 수 없다. [의견][^ref-1341][^ref-1454] 대화로 업무를 지시하는 일 자체는 [12. 채팅으로 업무 지시·오케스트레이션](../../categories/chat-based-configuration-and-operation/chat-task-instruction-and-orchestration.md)에서 다룬다.
