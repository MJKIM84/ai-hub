# 12. 명령·작업 실행의 신뢰성 — 대표 접근법과 기술

<!-- auto:page-status:start -->
> 페이지 상태: published · 신뢰도: medium · 페이지 버전: 1 · 마지막 갱신: 2026-09-25 · 마지막 실행: 2026-09-25
<!-- auto:page-status:end -->

## 1. 세 줄 요약

- 명령 실행 신뢰성의 기법은 식별자로 중복 거르기, 요청 단위 멱등성 키, 상태 기계, 시간 초과 감지, 재시도·취소·보상, 상태 저장과 재시작 복원으로 나눌 수 있다. [추정][^ref-031][^ref-366]
- 이 페이지는 [12. 명령·작업 실행의 신뢰성](../../categories/c-connectivity-and-execution-foundation/12-command-and-task-execution-reliability.md) 페이지의 "대표 접근법과 기술" 절이 분량 기준을 넘어 옮겨 온 것이다. 원 페이지의 검증을 거친 내용이며 새 주장은 없다.

## 2. 배경

[12. 명령·작업 실행의 신뢰성](../../categories/c-connectivity-and-execution-foundation/12-command-and-task-execution-reliability.md) 페이지를 쓰는 과정에서 "대표 접근법과 기술" 절의 분량이 세부영역 페이지 기준(4,000자)을 넘어, 내용을 줄이지 않고 이 주제 페이지로 분리했다.

## 3. 본문

명령 실행 신뢰성의 기법은 식별자로 중복 거르기, 요청 단위 멱등성 키, 상태 기계, 시간 초과 감지, 재시도·취소·보상, 상태 저장과 재시작 복원으로 나눌 수 있다. [추정][^ref-031][^ref-366]

### 식별자로 중복 거르기

VDA 5050 3.0.0 은 같은 주문 갱신 id 의 같은 내용은 무시하게 하고, 이전보다 낮은 주문 갱신 id 의 주문은 버퍼에 받지 않은 채 이전 주문을 유지하며 OUTDATED_ORDER_UPDATE 경고(WARNING)를 보고하게 한다. [사실][^ref-031] 이 명세는 order·instantActions·state 등 대부분의 토픽에 MQTT QoS 0(최선 노력)을, connection 토픽에 QoS 1(최소 한 번)을 쓰게 한다. [사실][^ref-031]

MQTT 5.0 의 QoS 2(정확히 한 번)는 네 단계 확인 교환으로 프로토콜 상대 사이의 정확히 한 번 전달을 보장하고, 수신 측은 교환이 끝날 때까지 패킷 식별자를 기억해 중복 PUBLISH 를 버린다. [사실][^ref-306] 이 보장은 클라이언트–브로커 같은 프로토콜 상대 사이에만 적용되므로, 관제가 시간 초과 뒤 새 메시지로 주문을 다시 보낸 경우의 중복은 주문 id·주문 갱신 id 같은 응용 계층 식별자로 걸러야 할 것으로 보인다. [추정][^ref-306][^ref-031] 통신 계층의 전달 보장 자체는 [11. 분산 시스템·통신·컴퓨팅 구조](../../categories/c-connectivity-and-execution-foundation/11-distributed-systems-communication-and-computing.md)에서 다룬다.

### 요청 단위 멱등성 키

IETF Idempotency-Key 헤더 초안은 키를 다른 내용의 요청에 재사용하지 않게 하고, 서버가 키 만료 정책을 공개하며, 원 요청이 처리 중일 때의 재요청에는 409, 다른 내용으로 재사용한 요청에는 422 를 돌려주도록 제안한다(검색 요약상 최신 게시판 -07, 2025-10-15). [사실][^ref-367] 반면 Open-RMF 의 작업 파견 요청과 작업 요청 스키마에는 요청자가 정하는 요청 식별자나 멱등성 키 필드가 없고, 요청 시각·가장 이른 시작 시각(unix_millis_earliest_start_time)·우선순위·범주·설명·라벨·요청자·플릿 이름만 두며, 작업 요청의 필수 필드는 category·description 뿐이다. [사실][^ref-365][^ref-125]

### 상태 기계로 진행 판정

ROS 2 액션은 목표 상태를 진행과 종료로 나누고, 서버가 결과를 설정한 시간 동안 캐시해 여러 클라이언트가 받을 수 있게 한다. [사실][^ref-363] OPC UA Part 10(Programs, v1.04 참조 페이지 기준)의 프로그램 상태 기계는 Halted·Ready·Running·Suspended 상태를 두며, Suspended 는 멈춘 지점에서 기능을 재개할 수 있는 상태이고 Halted 는 초기 상태이자 실패 또는 완료를 나타내는 종료 상태가 될 수 있다. [사실][^ref-368] PackML 로 알려진 ISA-TR88.00.02(2015판·2022판이 있음)는 Idle·Starting·Execute·Held·Suspended·Aborted 등 17개 기계·유닛 상태를 정의하는 것으로 알려져 있으나, ISA 원문 미열람이며 상태 목록은 발행 기관 자료로 미확인이다. [추정][^ref-369] Open-RMF 작업 상태 스키마는 queued·underway·completed·canceled·killed·failed 등 상태 값과 시작·종료 시각, 취소·강제 종료·중단 요청 기록을 담는다. [사실][^ref-111]

이 모델들은 일시정지·중단·취소·실패의 구분이 서로 달라(예: ROS 2 는 서버 자체 중단 ABORTED 와 외부 요청 CANCELED 를, Open-RMF 는 canceled 와 killed 를 구분), ROP 가 상위 시스템에 되돌릴 공통 작업 상태로 옮기려면 대응 규칙이 필요할 것으로 보인다. [추정][^ref-031][^ref-363][^ref-111][^ref-368][^ref-369]

### 시간 초과와 연결 끊김 감지

VDA 5050 3.0.0 에서 로봇은 상태 메시지를 관련 사건이 생길 때 또는 적어도 30초마다 발행해야 하고, 예기치 않은 연결 끊김은 브로커가 마지막 유언 메시지로 connectionState 를 CONNECTION_BROKEN 으로 알린다. [사실][^ref-031] ROS 2 는 deadline·liveliness QoS 정책과 그 위반 이벤트로 끊김을 감지하게 한다. [사실][^ref-282] 행동 트리 라이브러리 BehaviorTree.CPP 의 TimeoutNode 는 자식이 정해진 시간보다 오래 RUNNING 이면 중단(halt)하고 FAILURE 를 돌려준다. [사실][^ref-372] 다만 VDA 5050 명세 발췌 범위에서는 상태 메시지가 오지 않을 때 관제가 할 일을 찾지 못했으므로(부재 확정 아님), 시간 초과 기준과 그 뒤 처리(재질의·일시정지·사람 호출)는 30초 상태 주기와 CONNECTION_BROKEN 알림을 입력으로 ROP 가 따로 정해야 할 것으로 보인다. [추정][^ref-031]

### 재시도·취소·보상

VDA 5050 3.0.0 은 실패했지만 다시 시도할 수 있음을 뜻하는 동작 상태 RETRIABLE 을 두고, 관제가 즉시 동작 retry 로 재시도하거나 skipRetry 로 그 동작을 FAILED 로 넘기게 한다. [사실][^ref-031] cancelOrder 를 받은 로봇은 가능한 한 빨리 멈추고, 실행 중 동작이 모두 취소·종료될 때까지 RUNNING, 이동과 모든 동작이 멈춘 뒤 FINISHED 를 보고하며, 이후 관제는 취소된 주문에 갱신을 보내지 않는다. [사실][^ref-031] BehaviorTree.CPP 의 RetryNode 는 실패한 자식을 지정한 횟수까지 다시 실행한다. [사실][^ref-371]

Open-RMF 의 작업 취소 요청과 중단 요청은 작업 id(task_id)와 선택 라벨만으로 대상을 지정하고, 중단된 작업은 재개 요청을 보내야 다시 진행된다. [사실][^ref-126][^ref-127] rmf_task 에서 취소는 로봇을 짐 없는 상태로 되돌리게 하고, 강제 종료(kill)는 취소보다 우선해 로봇을 안전한 유휴 상태로 되돌리게 하며, 단계 건너뛰기(skip)·되감기(rewind)도 제공한다. [사실][^ref-366] 이미 화물을 싣거나 옮긴 물리 동작은 되돌릴 수 없으므로, 취소된 운반 작업의 복구는 사가의 보상 단계처럼 원위치 반송 같은 별도 작업을 새로 만들어 처리하는 형태가 될 것으로 보인다. [추정][^ref-373][^ref-031][^ref-366]

### 상태 저장과 재시작 뒤 복원

rmf_task 의 실행 중 작업은 순서 번호가 붙은 문자열 형태의 백업을 만들 수 있다. [사실][^ref-366] 그러나 플릿 어댑터 재시작 시 배정 작업이 사라지는 문제와 SQLite 기반 백업 저장 제안이 이슈로 제기되었고, 배포판 반영 여부는 미확인이다. [사실][^ref-374] ROS 2 관리형 노드(managed node) 설계는 Unconfigured·Inactive·Active·Finalized 네 주 상태와 전이 상태를 두어, 감독 도구가 모든 구성요소가 올바르게 준비되었는지 확인한 뒤 실행을 허용하고 노드를 운영 중에 재시작·교체할 수 있게 한다. [사실][^ref-364]
