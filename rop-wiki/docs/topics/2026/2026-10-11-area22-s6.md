## 3. 본문

공개 자료에서 확인한 접근법은 어댑터를 거친 요청·상태 감독, 요청–결과 방식의 작업대 인계, 관제의 구역 진입 허가 세 가지다. [사실][^ref-283][^ref-023][^ref-031]

### 어댑터를 거친 요청·상태 감독

Open-RMF 는 문과 승강기 앞에 어댑터를 두어 요청을 걸러 설비 노드에 전달하고, 승강기 노드는 OPC 같은 프로토콜로 승강기 제어기와 통신한다. [사실][^ref-283][^ref-284] 설비 상태는 문 모드와 승강기 상태 메시지로 되돌아온다. [사실][^ref-313][^ref-286] 한계는 이 구조가 Open-RMF 한 곳의 문서에 기댄다는 점이다.

```mermaid
flowchart LR
  req["요청자: 플릿 어댑터·핵심 시스템"] -->|승강기 요청| la["승강기 어댑터"]
  la -->|적절할 때만 전달| ln["승강기 노드"]
  ln --> lc["승강기 제어기 (연계 대상)"]
  ln -->|승강기 상태| req
  req -->|문 요청| da["문 어댑터"]
  da --> dn["문 노드"]
  dn --> dc["자동문 제어기 (연계 대상)"]
```

위 그림은 Open-RMF 문서 설명을 바탕으로 이 위키가 직접 그린 개념도다.

### 요청–결과 방식의 작업대 인계

배송 작업에서 로봇은 픽업 위치에서 디스펜서 서비스를 요청해 확인을 기다리고, 하역 위치에서 인제스터 서비스를 요청해 확인을 기다린다. [사실][^ref-023] 두 유형은 예시 구현이므로 실제 컨베이어·자동창고에 맞춘 어댑터는 현장마다 따로 필요하다. [추정][^ref-023]

### 관제의 구역 진입 허가

VDA 5050 3.0.0 에서 로봇은 상태 메시지의 zoneRequests 로 해제 구역 진입을 요청하고, 관제는 responses 토픽으로 허가·대기·철회·거절을 답한다. 허가가 철회·만료될 때의 행동은 releaseLossBehavior(정지·계속·대피)로 정한다. [사실][^ref-031] 동작 구역은 구역 진입·통과·이탈 때 미리 정한 action 을 수행하게 하는 장치이며, 명세는 이를 문·승강기 연동 수단으로 규정하지 않는다. [사실][^ref-031]

2026-10-11 재확인에서는 위 두 접근법(어댑터를 거친 요청·상태 감독, 요청–결과 방식의 작업대 인계)의 구현 세부와 제조사 어댑터·설비 쪽 연결 방식을 보강했다.

### 승강기 세션 감독과 수락 조건

Open-RMF 의 승강기 감독자(lift_supervisor) 구현(rmf_ros2 커밋 4cea3fe, 확인일 2026-10-11)은 승강기마다 활성 세션을 두고, 같은 세션 식별자의 새 요청은 갱신으로 다시 내보내며 세션 종료 요청이 오면 종료를 내보낸 뒤 활성 세션을 비운다. [사실][^ref-1436] 감독자에게 활성 요청이 없는데 승강기 상태에 세션이 남아 있으면 승강기가 풀리도록 세션 종료 요청을 계속 내보내며, 여러 요청 사이의 승강기 배정 규칙은 두지 않고 개선 과제(TODO) 주석만 남겨 두었다. [사실][^ref-1436] 플릿 어댑터 변경기록의 2.13.0(2026-06-15)에는 승강기가 이미 해당 층에 있으면 legacy 완료 상태를 내보내는 변경(#510)이 실려 있고, 같은 변경기록에는 그 뒤 판인 2.14.0(2026-09-26)도 있다. [사실][^ref-1398]

이 분석은 코드 동작과 설계 의도이며 현장 안전 동작의 재현이 아니다. 장치별 세션 수락 조건(AGV 모드 전환을 마친 뒤 session_id 를 보고하는지)을 어댑터 계약에 적고 수락 전 탑승을 막는지 확인하는 시험을 두며, 세션 유실·중복 종료·설비 상태의 세션 잔류 상황을 현장 인수 시험 항목에 넣는 것이 좋다는 것이 이 위키 구축자의 의견이다. [의견][^ref-1435][^ref-1436]

### 작업대 결과와 완료 판정

Open-RMF 배송 작업의 디스펜서 단계(DispenseItem) 구현은 요청 식별자가 일치하는 결과 메시지가 SUCCESS 이면 완료, FAILED 이면 실패로 바꾸고, ACKNOWLEDGED 는 접수 표시만 한다. [사실][^ref-1437] 같은 구현은 디스펜서 상태의 요청 대기열에 요청 식별자가 들어 있으면 접수로 보고, 접수 뒤 대기열에서 그 식별자가 사라지면 결과 메시지 없이도 완료로 간주한다. [사실][^ref-1437] 대기열 소거만으로 완료 처리하면 현장 작업대 대기열에서 요청이 취소·오류로 빠진 경우에도 인계 완료로 잘못 판단할 수 있을 것으로 보인다. [추정][^ref-1437] 그래서 실물 인계 성공을 뜻하는 센서·PLC 조건을 작업대 결과 메시지와 따로 정하고, 대기열 소거가 취소·오류를 뜻하는 경우를 구별해야 한다는 것이 이 위키 구축자의 의견이다. [의견][^ref-1437]

### 제조사 어댑터와 설비 자격증명

CHART 계열의 공개 KONE 승강기 어댑터 README(2023년 고정판을 KABAM-Robotics 저장소가 보존, 확인일 2026-10-11)는 Open-RMF 승강기 메시지와 KONE API v2.0 사이에서 WebSocket 으로 승강기 명령을 보내고 승강기 상태를 받는 구조를 설명한다. [사실][^ref-1438] 같은 README 는 실제 승강기를 제어하려면 접근 id 와 비밀값(access_id·access_secret)을 KONE 담당자에게서 받아야 한다고 안내한다. [사실][^ref-1438] 이 어댑터는 공개 구현이며 현행 KONE 계약을 보여 주지 않는다.

연계 대상: Open-RMF 의 Dormakaba 문 어댑터 README 는 시험한 EL301·ED250 문 구동기에 Dormakaba IoT connector 를 장착해야 하고, 문 클라우드 API 접근 자격증명은 Dormakaba 가 제공한다고 안내한다. [사실][^ref-1439] 제조사 어댑터를 검토할 때는 공개 어댑터의 판과 별도로 현행 API 판·권한 범위·건물 등록·세션 유지 조건을 확인하는 것이 좋다는 것이 이 위키 구축자의 의견이다. [의견][^ref-1438]

### 설비 쪽 연결 방식의 구분

제조사 API 대신 기존 승강기에 제어함과 PLC 를 새로 달아 드라이 접점으로 신호를 조작하는 방식도 한 도서관 현장 문서에 나온다(5절 기타 현장 사례). [추정] 벤더 주장[^ref-1440] 설비 API 연동과 로봇팔 버튼 조작을 서로 다른 승강기 연결 방식으로 기록하고, 공유 승강기 지연 시험을 따로 두는 것이 좋다는 것이 이 위키 구축자의 의견이다. [의견][^ref-163][^ref-943]
